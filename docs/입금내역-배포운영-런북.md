## 0. 무엇이 배포되나

```
[erp_macro]  ECOUNT 스크래핑 → 자기 DB(PII 암호화) → REST API
                                    ▲ HTTPS + X-API-KEY, 5분 주기 pull
[premium]    DepositSyncSchedule → bank_deposit 미러 upsert
             화면(GET /deposit/*) → 미러만 읽음
```

- 신규 테이블 **1개**: `bank_deposit` (프리미엄 소유 미러)
- 신규 엔드포인트 **3개**: `/deposit/list`, `/deposit/accounts`, `/deposit/sync-status`
- 신규 권한 **1개**: `UserAuthSubEnum.DEPOSIT_HISTORY` (정산관리 대분류)
- 신규 배치 **1개**: 5분 주기(`35 */5 * * * *`, KST) — **기본 꺼짐**

**기존 기능에 영향 없음.** 다른 테이블을 읽지도 쓰지도 않는다(표시명 조회를 위해 `wallet_account`/`user_company`를 **읽기만** 한다).

## 1. 배포 전 준비

### 1-1. 양측 액션

| # | 항목 | 담당 | 비고 |
|---|---|---|---|
| 1 | base URL · API 키 발급 (dev/prod 각각) | **erp_macro** | 안전 채널로 공유 |
| 2 | **프리미엄 서버 IP 전달** | **프리미엄** | 상대 인바운드 허용목록 등록용 |
| 3 | 미러 테이블 생성 | 프리미엄 | 1번 없이 **선행 가능** |

> 3번은 1·2번을 기다리지 않아도 된다. 키가 없으면 동기화는 꺼진 채로 뜨고 조회 화면은 정상 동작한다(빈 목록).

### 1-2. 운영 DB 접근

운영 RDS(`epopkon-prod`)는 **퍼블릭 액세스 off** — 의도된 구성이므로 **켜지 말 것.**
VPC 내 EC2를 경유한다. dev 는 로컬에서 직접 접속된다.

## 2. 배포 절차

### STEP 1 — 미러 테이블 생성 (코드 배포 **전**)

```sql
-- migration/bank-deposit-mirror.sql 전체 실행
```

**⚠️ 이 스크립트에는 `IF NOT EXISTS` 가 일부러 없다.** 구 설계의 `bank_deposit`(erp_macro 가 직접
write 하던 것)이 남아 있으면 **오류로 멈춘다** — 그게 "먼저 정리하라"는 신호다.

구 테이블이 있을 때의 절차:
```bash
mysqldump ... epopkon bank_deposit depositor_mapping deposit_polling_gate > backup.sql
```
```sql
DROP TABLE `bank_deposit`, `depositor_mapping`, `deposit_polling_gate`;
-- 그 다음 migration 실행
```
미러는 비어 있어도 무방하다 — 배치가 최초 1회 전체 백필로 채운다.

**검증**
```sql
SHOW CREATE TABLE `bank_deposit`;
-- 확인 포인트
--  · matched_owner_type / matched_owner_id 두 컬럼이 있는가
--  · CONSTRAINT chk_bank_deposit_matched_owner (CHECK) 가 있는가
--  · depositor 가 NULL 허용인가  ← NOT NULL 이면 구버전 스크립트다
```

### STEP 2 — 코드 배포

Gitea → 레포 → Actions → **`be-deploy-dev` 수동 실행**(push 만으로는 배포되지 않는다).

내부 동작: `git reset --hard origin/develop` → `npm install` → `npm run build` → `pm2 restart backend --update-env`

**검증** — 부팅 로그에 3개 라우트가 찍히는지
```
Mapped {/deposit/list, GET} route
Mapped {/deposit/accounts, GET} route
Mapped {/deposit/sync-status, GET} route
```

이 시점에 화면은 뜨지만 목록은 비어 있다(정상).

### STEP 3 — SSM 파라미터 등록

**⚠️ 서버 `.env` 에 넣지 말 것.** SSM 주입은 `process.env[key] === undefined` 일 때만 값을 채우므로,
`.env` 에 **빈 값으로라도 존재하면 그것이 이겨서** SSM 값이 무시된다.

경로: `/epopkon-premium/{dev|prod}/<키 이름>`

| 파라미터 | 타입 | 값 | 필수 |
|---|---|---|---|
| `ERP_MACRO_API_BASE_URL` | String | `https://<상대 도메인>` | ✅ |
| `ERP_MACRO_API_KEY` | **SecureString** | 발급 키 | ✅ |
| `DEPOSIT_SYNC_ENABLED` | String | `false` → 나중에 `true` | ✅ |
| `ERP_MACRO_API_TIMEOUT_MS` | String | `30000` | 선택(기본 30초) |
| `ERP_MACRO_STATUS_TIMEOUT_MS` | String | `3000` | 선택(기본 3초) |
| `DEPOSIT_SYNC_RESYNC_DAYS` | String | `30` | 선택 |
| `DEPOSIT_SYNC_PAGE_SIZE` | String | `500` | 선택 |
| `DEPOSIT_SYNC_BACKFILL_FROM` | String | `2020-01-01` | 선택 |

### 각 값이 어디서 쓰이나

| 키 | 사용 위치 | 하는 일 | 잘못 주면 |
|---|---|---|---|
| `DEPOSIT_SYNC_ENABLED` | `deposit.sync.service.ts` `isEnabled()` | 배치 on/off. **`'true'` 문자열과 정확히 비교** | `'True'`·`1` 등은 전부 꺼짐으로 해석 |
| `ERP_MACRO_API_BASE_URL` | `deposit.source.http.ts` `resolveConfig()` | 상대 도메인. 뒤에 `/api/deposits`, `/api/status` 를 붙인다 | 없으면 호출 자체를 안 하고 영구 실패 |
| `ERP_MACRO_API_KEY` | 〃 | `X-API-KEY` 헤더 값 | 불일치 시 401 → 영구 실패(재시도 무의미) |
| `ERP_MACRO_API_TIMEOUT_MS` | 〃 `fetchPage()` | 거래내역 조회 타임아웃. **배치 경로**라 넉넉히 | 너무 짧으면 큰 페이지에서 매번 타임아웃 |
| `ERP_MACRO_STATUS_TIMEOUT_MS` | 〃 `fetchStatus()` | 수집상태 타임아웃. **화면 요청 경로**라 짧게 | 길면 상대가 죽었을 때 조회 화면이 그만큼 멈춤 — 미러를 둔 의미가 사라진다 |
| `DEPOSIT_SYNC_RESYNC_DAYS` | `deposit.sync.service.ts` `resyncDays()` | 매 주기 다시 받아올 최근 구간(일) | 짧으면 뒤늦게 채워지는 회계전표를 놓침 |
| `DEPOSIT_SYNC_PAGE_SIZE` | 〃 `pageSize()` | 한 요청당 건수. 1~1000 으로 clamp | 2000 초과는 상대가 400 으로 거부. clamp 가 흡수 |
| `DEPOSIT_SYNC_BACKFILL_FROM` | 〃 `syncRecent()` | 미러가 원본보다 적을 때 백필 시작일 | 너무 이르면 페이지 상한(200)에 걸릴 수 있음 |

> **타임아웃이 두 개인 이유:** 같은 서버를 부르지만 성격이 정반대다. 거래내역은 5분에 한 번 도는
> 배치라 느려도 되고, 수집상태는 사람이 화면을 열 때마다 불린다. 하나로 합치면 둘 중 하나가
> 반드시 잘못된 값을 갖게 된다.

- 파라미터 **이름이 곧 환경변수 이름**이다(접두만 떼고 `process.env` 에 주입).
- 경로는 `ENVIRONMENT` 값에서 자동 유도된다. 서버에 `ENVIRONMENT=dev|prod` 가 설정돼 있어야 SSM 이 동작한다(없으면 조용히 `.env` 폴백).
- **값은 부팅 시 1회만 읽는다** → 바꾸면 재시작(=워크플로 재실행) 필요.

**검증** — 부팅 로그
```
[SSM] loaded N parameter(s) from /epopkon-premium/dev/
```
실패해도 앱은 뜬다(페일세이프). 그때는 `[SSM] failed to load ...` 경고가 찍힌다.

### STEP 4 — 도달 확인 (켜기 전)

```bash
curl -H "Authorization: Bearer <운영자 토큰>" https://<프리미엄>/deposit/sync-status
```

```jsonc
{
  "enabled": false,          // 아직 꺼짐 — 정상
  "lastSyncedAt": null,      // 아직 동기화 안 함 — 정상
  "source": {                // ★ 여기가 null 이 아니면 상대에 닿은 것
    "gateTripped": false,
    "gateReason": null,
    "lastScrapedAt": "2026-08-04T05:47:00.123456Z",
    "pollingEnabled": true
  }
}
```

- `source` 가 **`null` 이면 상대에 못 닿은 것** — IP 허용목록·도메인·키를 확인한다.
- `source` 가 채워지면 **키·회선·계약이 전부 정상**이다. 이제 켜도 된다.

### STEP 5 — 동기화 켜기

SSM 에서 `DEPOSIT_SYNC_ENABLED` 를 `true` 로 변경 → **워크플로 재실행**(재시작해야 반영).

**검증** — 5분 안에 로그에 찍힌다
```
[DEPOSIT_SYNC] 미러가 원본보다 4893건 적어 전체 백필을 수행합니다. (미러 0 / 원본 4893, from=2020-01-01)
[DEPOSIT_SYNC] 동기화 완료: 4893건 수신 (from=2020-01-01 to=2026-08-05)
```

로컬 실측: **4,893건 / 약 3초 / 10페이지**(size=500).

```sql
SELECT COUNT(*) FROM bank_deposit;                     -- 원본 건수와 일치해야 한다
SELECT match_status, COUNT(*) FROM bank_deposit GROUP BY match_status;  -- 전부 UNMATCHED 가 정상
SELECT depositor FROM bank_deposit LIMIT 1;            -- 암호문이어야 한다(평문이면 이상)
```

### STEP 6 — 권한 부여

`DEPOSIT_HISTORY` 는 운영자 **기본 권한에 없다**(의도적). SUPER_ADMIN 은 자동 포함.
다른 담당자에게 주려면 **프론트 권한관리 모달에 항목이 추가되어 있어야 한다**(§6 참조).

## 3. 운영 중 확인

### 정상 상태의 모습

| 신호 | 정상값 |
|---|---|
| `sync-status.enabled` | `true` |
| `sync-status.lastSyncedAt` | **5분 이내** |
| `sync-status.source.gateTripped` | `false` |
| 로그 | 5분마다 `동기화 완료: N건 수신` |

### 화면에서 "입금이 안 보인다"고 할 때

이 화면의 가장 위험한 오해는 **"수집이 멈춘 것"을 "입금이 없는 것"으로 읽는 것**이다.
그래서 `sync-status` 가 두 겹의 신호를 준다.

```
lastSyncedAt 이 방금  →  정상. 정말 입금이 없었던 것
lastSyncedAt 이 오래됨 →  프리미엄 동기화가 멈춤
source 가 null        →  상대 서버에 못 닿음
gateTripped = true    →  상대가 수집을 멈춤(운영자 개입 필요)
```

> **데이터 최대 지연은 8분**이다(상대 폴링 3분 + 프리미엄 pull 5분). 방금 입금한 건이 안 보이는 것은 정상이다.

## 4. 문제 진단표

| 증상 (로그/응답) | 원인 | 조치 |
|---|---|---|
| `ERP_MACRO_API_BASE_URL / ERP_MACRO_API_KEY 가 설정되지 않았습니다` | SSM 미등록, 또는 `.env` 의 빈 값이 SSM 을 이김 | `.env` 에서 해당 키 **제거** 후 재시작 |
| `동기화 영구 실패 — 설정/계약 확인 필요` + 401 | 키 불일치 | SSM 키 확인. 재시도해도 소용없다 |
| 같은 로그 + 400/404 | 계약 불일치(경로·파라미터) | 상대와 대조. `size` 가 2000 초과면 400 |
| `동기화 일시 실패 — 다음 주기에 재시도합니다` | 5xx·타임아웃·네트워크 | 대개 자동 수렴. 반복되면 회선 확인 |
| `수집 상태 조회 실패` (warn) + `source: null` | 상대 `/api/status` 에 못 닿음 | 화면은 정상 동작. IP 허용목록 확인 |
| `erp_macro 수집이 차단된 상태입니다: <사유>` | 상대 안전 게이트 작동 | **상대 운영자 수동 리셋 필요** |
| `페이지 상한(200)에 도달해 중단했습니다` | 원본이 10만 건 초과 | `DEPOSIT_SYNC_BACKFILL_FROM` 을 좁혀 나눠 백필 |
| `이전 동기화가 아직 진행 중이라 이번 주기를 건너뜁니다` | 앞 주기가 안 끝남 | 정상. 10분 넘으면 stale 로 자동 해제 |
| `Table 'bank_deposit' doesn't exist` | STEP 1 누락 | 마이그레이션 먼저 |
| 목록 조회 500 | 위와 동일 가능성 | 테이블 존재 확인 |
| 목록에 **암호문**이 보임 | 상대가 암호문을 그대로 줌(계약 위반) | 상대 확인. 우리는 평문을 받아 암호화 저장한다 |

### 로그 태그

```
[DEPOSIT_SYNC]  동기화 배치
[DEPOSIT]       조회 서비스(감사 로그 적재 실패 등)
[SSM]           파라미터 주입
```

## 5. 되돌리기

**동기화만 끄기 (가장 안전)**
```
SSM: DEPOSIT_SYNC_ENABLED = false  →  재시작
```
화면은 계속 뜨고 미러 데이터도 남는다. 상대 호출만 멈춘다.

**화면까지 내리기**
develop 에서 되돌린 뒤 재배포. `bank_deposit` 테이블은 **지우지 않아도 된다**(다른 기능이 참조하지 않음).

**미러 데이터만 초기화**
```sql
TRUNCATE TABLE bank_deposit;   -- 다음 주기에 전체 백필로 자동 복구
```
> 단, **매칭 기능이 가동된 뒤에는 금지.** 그때는 `matched_owner_*` 가 재생성 불가능한 프리미엄 원장이 된다.

## 6. 프론트 작업 (별도 저장소, 미착수)

`epopkon-premium-front`. **권한 키를 3곳에 넣어야 하고 하나라도 빠지면 조용히 샌다.**

| 파일 | 할 일 | 빠뜨리면 |
|---|---|---|
| `src/types/Permission.ts` | `UserAuthSubEnum` 에 `DEPOSIT_HISTORY` | 컴파일 에러 |
| `src/components/PermissionManagementModal.tsx` | 중복 enum + 정산관리 체크박스 | **아무에게도 권한을 못 준다** (SUPER_ADMIN 제외) |
| `src/constants/route.tsx` | `SUB_MENU` + `authKey` | **SSR 게이트가 fail-open** — 권한 없어도 페이지가 열림 |

**계약 호환성은 확인 완료** — 응답 봉투(`ISearchResponse`), 페이징 필드명, 날짜 포맷 모두 프론트 관례와 일치한다.

렌더링 주의 3가지
1. `txType` 이 `null` 일 수 있음 → `txTypeLabel`(한글 원문)로 폴백. 모르는 값을 임의로 접지 말 것
2. `source` 가 `null` 일 수 있음 → 화면은 계속 떠야 함
3. `pollingEnabled` 가 `null` 이면 "꺼짐"이 아니라 **"모름"**

`scrapedAt`/`lastSyncedAt` 은 DTO 타입이 `Date` 지만 HTTP 를 건너면 ISO 문자열이다 → 프론트 타입은 `string`.

## 7. 검증 도구

### 스모크 스크립트 (실 MySQL)
```bash
npx ts-node -r tsconfig-paths/register src/deposit/deposit.smoke.ts
```
일회용 DB(`epopkon_deposit_smoke`)를 만들어 18항목을 검사하고 지운다. **기존 DB 는 건드리지 않는다.**
DDL↔엔티티 정합, 실제 키로 암호화 왕복, 프리미엄 컬럼 보존, CHECK 제약을 확인한다.

### 단위 테스트
```bash
npx jest src/deposit src/common/api/logger.middleware.spec.ts
```

### 로컬 E2E (상대 API 없이)
`erp_macro` DB 를 읽어 상대 명세 형태로 응답하는 stub 을 9099 포트에 띄우고,
`.env.local` 에 `ERP_MACRO_API_BASE_URL=http://127.0.0.1:9099` 를 넣어 앱을 띄우면 전체 흐름을 재현할 수 있다.
(상대 DB 의 PII 는 암호문이므로, stub 이 고유 암호문마다 결정론적 평문을 배정해 실제 API 를 흉내내야 한다)

## 부록: 변경 시 사전 협의가 필요한 것 — **하나뿐**

> ### `dedupKey` 산식과 정규화 규칙
> `SHA-256(계좌 | 일자 | 구분 | 금액 | 잔액 | 입금처)`, 입금처 `(가상)` 제거 + trim, `voucherNo` 제외
>
> 바뀌면 같은 거래가 새 지문으로 들어와 **같은 입금이 두 줄** 생긴다. 자동 감지 수단이 없고
> 발견 시점에는 이미 중복이 쌓여 있다. 공백 처리 하나만 바뀌어도 전 건의 지문이 달라진다.

나머지(필드 추가, 봉투 키 추가, 정렬 기본값 변경)는 프리미엄이 모르는 값을 무시하므로 협의 없이 바꿔도 깨지지 않는다.
