# 후속: /order/delivery-cancel 소유권 검사 (보안) — **해결됨**

> 상태: **해결(197-16 브랜치 내에서 처리)**. 별도 티켓 불필요.
> 최초 근거: 197-16 리뷰(code-reviewer / architect lane). 이후 관리자 리뷰가 같은 건을 **P1 보안**으로
> 재지적해, 후속으로 미루지 않고 이 브랜치에서 닫았다.
> 이 문서는 "왜 이렇게 막았는가" 의 근거로 남긴다.

## 문제 (당시)

`POST /order/delivery-cancel` 은 **메서드 레벨 소유권 가드가 없었다**. 클래스 가드
`AuthUserAuthorizationGuard` 는 JWT 유효성만 검증하고, 서비스의 `order.userId = :userId` 조건도 주석 처리돼 있었다.

→ 인증된 아무 사용자나 **주문 id 만 알면 타 테넌트의 예약 발송을 취소**시킬 수 있었다.
   환불은 그 주문 명의로 가므로 금전 탈취는 아니고 **서비스 방해(발송 취소)** 다.
   부분취소 경로는 애초에 `user` 를 인자로 받지도 않아 검사 자체가 불가능한 상태였다.

## 이미 막혀 있던 것 (오해 방지)

- `deliveryIds` 로 **타 주문의 발송건**을 취소하는 것은 불가능했다. CAS 의
  `EXISTS(... AND opm.order_id = :orderId)` 가 정확히 막는다(197-16 로컬 QA T5 로 실증: 타 주문 발송건 혼입 → 400,
  내 주문·타 주문 모두 미취소·미환불).
- 즉 노출은 "남의 **주문 전체/그 주문의 발송건**을 취소" 로 한정되며, 크로스 주문 발송건 혼입은 아니었다.

## 조치

`deliveryCancel` 진입부에서 `assertOrderInViewScope(user, id)` 를 **전체취소·부분취소 양쪽 앞**에 호출한다
(`src/order/application/order.service.ts`). 회귀 테스트: `order.service.cancel-ownership.spec.ts` 4케이스
— 범위 밖이면 부분취소 경로 미진입 / 주문 행 잠금 미도달, 범위 안이면 종전대로 통과.

### 판정 기준을 `applyViewScopeFilter` 로 고른 이유

`canTransitionDelivery`(발송확정 권한)는 SUPER/OPERATION 전용이라, 자기 주문을 취소하던
고객사(CORPORATE_ADMIN)까지 막혀 **동작이 바뀐다**. 여기서 필요한 것은 "남의 주문을 못 건드린다" 이므로
조회범위 기준이 정확하고 기존 동작을 보존한다.

회귀가 없다는 근거는 **집합 포함관계**다. 주문목록은 `applyViewScopeFilter` **에 더해**
`applyDirectSendingFilter` 와 `status != TEMP` 를 AND 로 걸고, 주문상세는 동일 스코프를 건다. 반면 이 검증은
스코프만 본다.

> 화면에서 취소 버튼에 도달할 수 있던 사용자 ⊂ 새 검증을 통과하는 사용자

즉 새로 막히는 대상은 **애초에 주문상세를 열 수 없던 호출자**뿐이며, 그게 이 조치가 막으려던 것이다.

### 착수 조건이던 "403" 을 400 으로 바꾼 이유

최초 문서는 회귀 테스트를 `403` 으로 적었으나 구현은 **400('주문이 존재하지 않습니다')** 이다.
조회 API 와 동일한 응답이라 **그 주문이 존재하는지 자체를 알려주지 않는다** — 403 은 "있지만 권한 없음" 을
확인해 줘서 id 순회로 타사 주문의 존재 여부를 캐낼 수 있다. 의도된 선택이다.

## 남은 관찰 (별건, 이 문서의 범위 아님)

- 같은 화면의 인접 액션(검토완료·발송확정)은 `canTransitionDelivery`(권한 기준)로 판정해 술어가 다르다.
  결과적으로 "스코프 밖 직발송 건을 운영자가 발송확정은 되는데 취소는 안 되는" 역전이 생긴다.
  UI 에 그 id 획득 경로가 없어 현재 드러나지 않으며, 통일한다면 **발송확정 쪽을 조이는** 방향이어야 한다.
- CS·정산 화면 일부 목록은 view_scope 없이 `order.id` 를 노출한다. 그 id 로 취소 API 를 직접 호출하던
  운영 관행이 있었다면 이제 400 이 된다 — 이번 조치가 명시적으로 막으려던 대상이지만, 배포 전 운영 확인 권장.
