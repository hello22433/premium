# 설계: 첨부파일 저장 보안 + 다운로드 파일명 정정

작성일: 2026-06-29 / 대상: epopkon-premium(BE) + epopkon-premium-front(FE)

---

## 1. 배경 & 문제 정의

주문접수·문서함에서 엑셀 첨부를 내려받으면 파일명에 **난수(=업로드 시각 `Date.now()` 접두사)** 가 붙어서 저장된다. 추적해 보니 단순 UX 문제가 아니라 **보안 비대칭**과 한 뿌리였다.

- 공용 업로드 `uploadFile()` 은 **`ACL: public-read` + `file/{Date.now()}-{원본명}`** 키로 저장한다. (`src/file/infra/file.storage.s3.ts:57-80`)
- 주문접수/문서함 첨부는 이 공용 경로(`POST /file/upload`)를 그대로 탄다. 저장된 **S3 public URL** 을 DB(`order_receipt.filePath`, 콤마구분)에 넣고, 프론트는 그 URL을 **백엔드 프록시 없이 `<a href target=_blank>` 로 직접** 연다.
- 따라서 ① 링크만 알면 **인증 없이 누구나 다운로드**(public-read), ② 키가 **시각 기반이라 추측/열거 가능**(Date.now), ③ 다운로드 파일명이 키 그대로(`{타임스탬프}-{원본명}`) 나온다.

### 1.1 왜 지금까지 안 고쳐졌나 (근거)

- 동일 취약점 클래스는 **2026-06-08 `0ff470e`** 에서 이미 인지·수정됐다. 단, **공유 상품리스트 호출처만** `uploadPrivateFile` 로 교체하고 *"공용 uploadFile(PDF/이미지 등 public URL 반환 호출처)은 그대로 유지"* 로 남겼다.
- 같은 시기 쿠폰 이미지에서 **`Date.now 단독 → ms brute-force 대량 수집`** 을 PoC로 확인하고 **UUID로 봉합**(`dc43679`)했다. → 팀은 "Date.now는 약하다"를 명확히 알고 있었다.
- 그러나 **주문접수·문서함은 감사(담당3, 06-04~08) 스코프 밖**이라 findings에 0건. 공용 `uploadFile` 을 타는 *민감 호출처 전수*를 아무도 하지 않아 **사각지대로 누락**된 것이다. (의식적 허용 아님)
- 사용자가 기억한 "nginx 안전 판단"은 `.env`/dotfile 정적 노출 한정 결론(06-04 §7-4(1))이고, `public/` 안의 *파일 내용*은 오히려 위험으로 분류했다. 주문접수와 무관.

→ **결론: 이번 작업은 6/8 작업의 못다 한 후속편이며, 보안(ACL·열거)과 파일명 문제가 한 수정으로 함께 풀린다.**

## 2. 현황 분석

### 2.1 저장소 비대칭 인벤토리

| 기능 | 메서드 | ACL(축A) | 파일명(축B) | 민감 | 판정 |
|---|---|---|---|---|---|
| **주문접수 첨부** | `uploadFile` | 🔴 public | 🔴 Date.now | 예 | 🚨 둘 다 취약 |
| 공용 `/file/upload`(문서함·QnA·문의·공지 첨부 공유) | `uploadFile` | 🔴 public | 🔴 Date.now | 일부 | ⚠️ 동일 경로 |
| 일반 이미지 업로드 | `uploadImageFile` | 🔴 public | 🔴 Date.now | 아니오 | 🟡 낮음 |
| 외부 이미지 복사 | `copyImageFromUrl` | 🔴 public | 🔴 Date.now | 아니오 | 🟡 낮음 |
| QR 코드(쿠폰 발송) | `uploadImageFileWithBuffer` | 🔴 public | 🟢 UUID | 예(추정) | ⚠️ ACL만 |
| 쿠폰 이미지 | `public/` 디스크 | 🔴 public(dir) | 🟢 UUID | 예 | ⚠️ 의도 유지(Gemtek) |
| **공유 상품리스트** | `uploadPrivateFile` | 🟢 private | 🟢 UUID | 예 | ✅ 고침(0ff470e) |
| 내보내기 엑셀 | `createExportTempPath` | 🟢 tmp | 🟢 UUID | 예 | ✅ 안전(b521e84) |

두 축: **A=ACL(public-read vs private)**, **B=파일명(Date.now 열거가능 vs UUID 랜덤)**. *둘 다* 나쁜 진짜 사각지대는 **공용 `uploadFile` 경로 하나**.

### 2.2 다운로드 경로 & 프론트 의존성

- 주문접수: `OrderReceiptDetailPage.tsx` 가 `data.filePathList` 의 S3 URL을 `<a href={fileUrl} target="_blank">` 로 직접 오픈. **백엔드 프록시 없음.**
- **파일명 표시 파싱이 FE 5곳**에 존재: `fileName.split('-').slice(1).join('-')` (키 = `{한덩어리}-{원본명}` 가정, 하이픈 1개).
  - `OrderReceiptDetailPage.tsx:25`, `SendRealItemOrderPage.tsx:807`, `QnaDetailPage.tsx:423`, `NoticeDetailPage.tsx:283`, `DocumentDetailPage.tsx:379`
  - ⚠️ `randomUUID()` 는 하이픈 4개 → 이 파싱이 전부 깨진다. → **하이픈 없는 UUID(`replace(/-/g,'')`) 필수.**
- 프론트 인증 = **Bearer 토큰**(쿠키→axios interceptor가 `Authorization` 주입, `src/utils/request.ts:133`). → private 프록시는 `<a href>`/`window.open` 불가, **`request({responseType:'blob'})` 필요.**
- **선례(그대로 차용)**: 공유리스트 다운로드 = `GET /product/shared-list-file/download`(blob) + `src/utils/fileHelper.ts` 가 응답 `content-disposition` 에서 `filename=` 추출해 저장.

## 3. 설계 원칙

외부 노출이 필요한지로 분기한다.

- **외부 노출 필요(이미지 등)** → **public 유지 + 파일명만 UUID화**(열거 차단). 인라인 표시를 깨면 안 되므로 `attachment` 헤더 금지.
- **민감 문서(주문접수·문서함 등)** → **private 전환 + 백엔드 다운로드 프록시**. 프록시가 `Content-Disposition` 으로 원본명 강제 → 보안·파일명 동시 해결.

UUID는 **전 구간 하이픈 없는 32hex 로 표준화**(`randomUUID().replace(/-/g,'')`)하여 ① FE 파싱 무변경 ② 키에서 원본명 복원(`split('-').slice(1)`) 일관성 확보.

## 4. 트랙 1 — public 이미지 UUID화 (작음, 무중단)

### 변경 (BE만)
`src/file/infra/file.storage.s3.ts` 의 public 키 생성에서 `Date.now()` → `randomUUID().replace(/-/g,'')`:
- `uploadImageFile` (`image/{uuid}-{name}`)
- `uploadFile` (`file/{uuid}-{name}`) — *비민감 잔류분*(공지 이미지 등). 단 트랙2에서 민감 호출처는 별도 분리.
- `copyImageFromUrl` (`image/{uuid}-{name}`)

### 영향/리스크
- FE 5곳 파싱: 하이픈 없는 UUID라 `split('-').slice(1)` **그대로 동작 → FE 무변경.**
- BE에 Date.now 접두사 파싱 의존성 **없음**(확인 완료, 주석 데드코드만).
- 기존 객체는 그대로(혼재 허용). 신규 업로드부터 열거 차단.

### (선택) 이미지 다운로드명도 원본으로
원하면 키를 **폴더형 `image/{uuid}/{원본명}`** 으로. URL 끝=원본명 → 직접 다운로드명도 깨끗 + 인라인 유지. 단 FE 5곳을 `split('/').pop()` 만 쓰도록 단순화 필요. → **결정필요 D2.**

### 테스트
`file.storage.s3.*.spec` 에 "public 키가 UUID(하이픈 없음) 포함·매 호출 고유·Date.now 미사용" 회귀 가드 추가.

## 5. 트랙 2 — 민감 첨부 private + 다운로드 프록시 (중간)

대상: **주문접수 첨부** (+ 결정 시 문서함/QnA/문의 — **D1**).

### 5.1 업로드 (private 전환)
- 신규 엔드포인트 **`POST /file/upload-private`** 추가 → `fileService` → `uploadPrivateFile()`(이미 존재, `private/{uuid}-{name}`, ACL private). `uploadPrivateFile` 의 UUID도 **하이픈 제거로 표준화**(공유리스트는 DB의 `fileName` 으로 표시하므로 영향 없음).
- 주문접수/문서함 FE 업로드 호출을 `postFileUpload` → `postFileUploadPrivate` 로 교체. 반환 URL(`https://.../private/...`)을 기존처럼 `filePath` 에 저장. 이 URL은 이제 **직접 접근 불가**, 프록시로만 받는다.

### 5.2 다운로드 프록시 (신규 엔드포인트)
**`GET /order-receipt/:id/file/download?fileUrl=<stored-url>`** (기존 컨트롤러 가드 재사용)
1. `:id` 주문접수 조회 + **요청자 권한 검증**(기존 상세조회와 동일: 기업관리자=본인 문서만).
2. `fileUrl` 이 해당 receipt 의 `filePath`(콤마분리) **목록에 포함되는지 검증** → IDOR 차단.
3. URL → S3 key 추출(`extractStorageKey`, 기존 `file.service.ts:67`), `GetObjectCommand` 스트리밍.
4. 원본명 복원: `key.split('/').pop().split('-').slice(1).join('-')` (하이픈 없는 uuid 표준화 전제). 디코드 후
   `res.setHeader('Content-Disposition', "attachment; filename=\"<ascii fallback>\"; filename*=UTF-8''<encodeURIComponent(원본명)>")`.
   `Access-Control-Expose-Headers: Content-Disposition` 도 설정(기존 다운로드들과 동일).
   ※ FE `fileHelper.ts` 가 현재 `filename=` 만 파싱 → **`filename=` 토큰을 반드시 포함**(위 형식이 충족). RFC5987 `filename*` 도 같이 두어 한글 보장.

### 5.3 FE 변경
- `<a href={fileUrl}>` → **다운로드 버튼**: `request<Blob>({ url: `${PROXY}/order-receipt/${id}/file/download`, params:{ fileUrl }, responseType:'blob' })` 후 `fileHelper` 로 저장(공유리스트 패턴 동일).
- 표시명은 기존 `getDisplayFileName` 유지(하이픈 없는 uuid라 정상).

### 테스트
- BE: 프록시 권한 통과/거부, **IDOR(타 receipt fileUrl 주입 차단)**, Content-Disposition 원본명/한글, 스트림 정상, private ACL 회귀.
- FE: 다운로드 파일명 = 원본명, 권한별 노출.

## 6. 마이그레이션 (기존 데이터)

- **기존 public 객체**(주문접수 등 과거 업로드): 두 가지 처리 필요 — **D3**.
  - (a) 운영(코드 밖): 기존 S3 객체 ACL을 private 일괄 변경 + 버킷 ListBucket 점검(0ff470e 미결과 동일선상).
  - (b) 코드: 프록시의 key 추출/원본명 복원이 **구 키(`file/{Date.now}-{name}`)와 신 키(`private/{uuid}-{name}`) 둘 다** 처리하도록 일반화(앞 1글자 세그먼트만 떼는 방식이라 양쪽 호환). 단 (a) 전에는 구 객체가 private가 아니라 프록시가 GetObject는 가능하나 공개도 유지됨 → (a) 완료가 보안 종결 조건.
- 미적용 시: 신규 업로드만 안전, 기존은 그대로. 최소한 신규부터 닫는 것을 1차 목표로.

## 8. 결정 (확정 — 2026-06-29)

- **D1 ✅ 주문접수만 먼저.** 문서함/QnA/문의/공지는 민감도 확인 후 후속 트랙.
- **D2 ✅ 이미지=UUID화만**(열거 차단, FE 무변경). 폴더형 안 씀. 다운로드 원본명은 *문서(트랙2)* 의 프록시가 책임진다(이미지는 표시용이라 다운로드명 무관).
- **D3 ✅ 코드 호환만.** 프록시가 레거시 키(`file/{Date.now}-`)도 처리. 기존 객체 ACL 일괄변경은 이번 범위 밖(운영 후속).
- **원본명 ✅ 키에서 복원(최소 변경).** `order_receipt` 에 파일명 컬럼 추가 안 함. `private/{uuid}-원본명` 에서 `split('-').slice(1)` 로 복원 → **UUID 하이픈 표준화가 전제.** 레거시 `file/{Date.now}-원본명` 도 동일 복원식으로 호환(Date.now엔 하이픈 없음).
- (별도 트랙) QR 코드 private화: 열거는 이미 UUID로 막힘 → 후속, 우선순위 하향.
