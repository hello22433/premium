# 입금내역 2단계(매칭·충전) 선결 과제

> 작성: 2026-08-05 · 대상: `feat/deposit-list` 다음 단계
> 1단계(목록 조회 + erp_macro 동기화) 리뷰에서 나왔으나 **범위 밖이라 미룬** 항목들이다.
> 전부 **기존 자금 도메인(wallet/settlement-code)의 성질**이며 1단계가 만든 결함이 아니다.
> 다만 매칭·충전이 붙는 순간 경계에서 문제가 되므로, 그 코드를 짜기 전에 결정해야 한다.

---

## 왜 지금 안 고쳤나

1단계 범위는 **입금내역 조회 + 계좌 스크래핑 동기화**로 한정했다. 아래 셋은 전부 "충전 기능"에
붙는 것이고 그 코드가 아직 없다. 남의 도메인 테이블을 미리 바꾸는 것은 위험만 크고 이득이 없다.

기존 시스템은 자기들끼리 일관되어 있었다. 문제는 **미러(BIGINT, 문자열 코드 참조)와 자금
도메인(INT, 참조자 2곳)이 만나는 지점**이며, 그 지점은 아직 존재하지 않는다.

---

## ① 금액 타입 — 미러 BIGINT ↔ 지갑 INT

| 위치 | 타입 |
|---|---|
| `bank_deposit.amount` / `balance` | **BIGINT** (`migration/bank-deposit-mirror.sql`) |
| `wallet_account.deposit_balance` / `credit_limit` | **INT** (`src/entity/wallet.account.entity.ts`) |
| `wallet_transaction.amount` | **INT** |
| `chargeDeposit` 검증 | `Number.isInteger && > 0` — **상한 없음** |

미러가 BIGINT 인 것은 취향이 아니라 상대 API 가 `long` 을 주기 때문이다(주석: "INT 상한을 넘을
수 있어 BIGINT"). 받은 값을 INT 로 좁히면 그 자리에서 잘린다.

**21억(INT 상한, 2,147,483,647)을 넘는 입금 한 건**을 그대로 충전에 연결하면 strict mode 에서
out-of-range 로 실패하거나 잘린다. 게다가 미러 응답이 이미 `Number()` 로 좁히고 있어
(`deposit.service.ts`) 조용히 넘어갈 소지가 크다.

**결정할 것:** 충전 연결 지점에서 상한 검증으로 막을지, 지갑을 BIGINT 로 올릴지.
후자는 정산·주문·여신 전 경로에 영향이 가므로 다른 팀 코드까지 검증이 필요하다.

---

## ② 충전 멱등키 — `requestKey` 를 무엇에서 파생할 것인가

`chargeDeposit` 은 **호출자가 준 `requestKey`** 기반으로 멱등을 보장한다
(`settlement-code-admin.service.ts`, `idempotencyKey = hash(walletId, requestKey)`).

충전(wallet_transaction)과 `bank_deposit.match_status = CREDITED` 는 **다른 트랜잭션**이다.
충전은 성공했는데 상태 갱신이 실패하는 구간이 존재한다. 이때 재시도가 안전하려면 `requestKey` 가
반드시 **입금 건에서 결정론적으로 파생**되어야 한다.

```
권장: requestKey = `BANK_DEPOSIT:${dedupKey}`
```

화면이 매번 새 uuid 를 만들어 보내면 **같은 입금이 두 번 충전된다.** 멱등키가 `(walletId,
requestKey)` 해시라서 막아주지 못한다. 중간 테이블 없이 갈 거라면 이 규칙이 유일한 방어선이다.

**결정할 것:** `dedup_key` 파생 규칙으로 고정할지, `deposit_charge_request` 같은 중간 테이블을 둘지.

---

## ③ 정산코드 rename 시 `matched_owner_id` 고아화

`renameCode` 는 `wallet_account.owner_id` 와 해당 회사 `user.settlement_code` **둘만** 갱신한다.
그때는 참조자가 그 둘뿐이었기 때문이다. `bank_deposit.matched_owner_id` 는 FK 없는 논리 참조라
(`migration` 주석) rename 후 **고아**가 된다.

- 표시명이 `null` 이 된다(`loadMatchedOwnerNames` 가 못 찾음)
- 그 상태로 충전을 시도하면 `wallet_account 를 찾을 수 없습니다` 로 실패한다

**결정할 것 (택1)**

| 안 | 내용 | 대가 |
|---|---|---|
| A | `renameCode` 트랜잭션에서 `bank_deposit.matched_owner_id` 도 함께 갱신 | 변경 범위 작음. 현재 컬럼 설계 유지 |
| B | 귀속 키를 불변인 `wallet_account.id` 로 변경 | rename 무관. 단 화면에 코드를 보이려면 매번 조인, "정산코드 단위"라는 의미가 흐려짐 |

> **B 를 고를 거라면 컬럼이 비어 있는 지금이 가장 싸다.** 매칭이 값을 채우기 시작하면 이관이 필요하다.
> 다만 정산코드 rename 이 실제로 얼마나 일어나는지는 운영 사실이라, 빈도가 0 이면 없는 문제다.

## ④ (참고) 범위 밖으로 남긴 그 외

| 항목 | 내용 |
|---|---|
| 금융 PII 암호화 seam | `crypto.cipher.ts` 에 "전용키/랜덤IV 전환 시 여기만 교체" 라는 금융 PII seam 이 있는데 deposit 은 `encryptDeliveryTarget` 을 직접 부른다. 지금은 두 메서드가 같은 구현이라 동작 동일. **Option B 전환 시 deposit 만 남는다.** 공용 모듈이라 1단계 범위 밖 |
| `needsBackfill` 총계 비교의 상쇄 | `mirrorCount < sourceTotal` 은 "유령 행 5건 + 미수신 5건"이 동시에 있으면 같아져 자가치유가 발동하지 않는다. 미러가 삭제를 하지 않기 때문. 실현 조건이 좁아 미룸 |
