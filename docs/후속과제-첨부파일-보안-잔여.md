# 후속과제: 첨부파일 보안 — PR #44 에서 미룬 것

작성일: 2026-08-14 / 대상: epopkon-premium(BE)
선행: `설계-첨부파일-보안-및-다운로드파일명.md`, PR #538(주문접수 · 머지됨), PR #44(문서함)

PR #44(문서함 첨부 private 전환)의 리뷰 과정에서 확인됐으나 **그 PR 범위 밖이라 미룬 것들**을 근거와 함께 남긴다.
근거 없이 사라지면 나중에 같은 것을 다시 설계하게 되므로, **왜 미뤘는지**를 같이 적는다.

⚠️ **아래 1·2 는 PR #44 가 만든 게 아니라 develop 에 이미 있는 결함이다.** PR #44 는 문서함(user_drive)
한정으로 같은 클래스를 닫았고, 형제 기능인 주문접수(order_receipt)는 손대지 않았다.
**공용 util 에 헬퍼가 올라갔다고 형제 기능이 함께 안전해진 것이 아니다.**

## 1. [높음] 주문접수 상세조회가 임의 S3 key 를 조회한다 — 파일명 유출 + 승인 차단

### 무엇

`src/order_receipt/application/order.receipt.service.ts:141-150`

```ts
const fileUrlList = parseFilePathList(receipt.filePath);
const files = await Promise.all(
  fileUrlList.map(async (url, index) =>
    index < OrderReceiptService.MAX_FILE_META_LOOKUP
      ? { url, name: await this.fileService.getOriginalName(url) }   // ← 무조건 HeadObject
      : { url, name: this.fileService.extractOriginalFileName(url) },
  ),
);
```

- `isOwnStorageUrl`(우리 버킷인지) 검사 **없음**
- 객체 소유 검사 **없음**
- 항목별 `try/catch` **없음**

`getOriginalName` → `extractStorageKey` 는 **임의 host 의 pathname 을 우리 버킷 key 로 취급**한다.

### 왜 문서함보다 위험한가 — 쓰기 노출면이 더 넓다

| | 문서함(user_drive) | 주문접수(order_receipt) |
|---|---|---|
| 첨부를 넣을 수 있는 사람 | **관리자 전용** (create/update 가 CORPORATE_ADMIN 차단) | **기업관리자 셀프서비스** |
| 쓰기 시점 소유 검증 | 있음 (PR #44) | **없음** (`filePath.join(',')` 만) |
| 읽기 시점 이름 노출 판정 | 있음 (PR #44 `resolveHeadableUrls`) | **없음** |

### 재현 가능한 두 가지

**(a) 원본 파일명 유출**
기업 사용자가 `filePath: ["https://{버킷}.s3.amazonaws.com/private/77/xxx-대외비계약서.pdf"]` 로 접수를 생성
→ 본인 상세조회(`assertCanReadReceipt` 통과)
→ HeadObject 메타데이터의 **진짜 원본명**이 `files[].name` 으로 응답에 실려 내려온다.
다운로드는 `order.receipt.service.ts:232`(`ownerId !== user.id`)가 막지만 **이름은 안 막는다.**

**(b) 관리자 승인이 항상 500 + 롤백**
`OrderReceiptCreateReqDto.filePath` 는 `@IsString({each:true})` 뿐이라 임의 문자열이 통과한다.

| 심는 값 | 터지는 곳 | 결과 |
|---|---|---|
| `["not-a-url"]` | `getDetail` 의 `new URL` TypeError | 그 접수 건 상세가 **본인·관리자 양쪽에서 영구 500** |
| `https://{버킷}.s3.amazonaws.com/private/{자기id}/%` | `auto.order.service.ts:595` `assertAttachmentReadable` 의 `decodeURIComponent` URIError | **관리자 승인(approve)이 항상 500 + 트랜잭션 롤백** |

(b) 두 번째는 소유검사(`ownerId === receipt.userId`)를 정상 통과하므로 권한으로 막히지 않는다.
**기업 사용자가 자기 접수의 결재를 영구히 막을 수 있다.**

### 고치는 순서 (문서함에서 검증된 순서 그대로)

1. `getDetail` 에 **항목별 try/catch 폴백** (user_drive `user.drive.service.ts:121-131` 참조) — 영구 500 을 먼저 막는다
2. `extractStorageKey` 호출을 **감싸서** 쓰기 400 / 읽기 4xx 로 (user_drive `tryExtractStorageKey`)
3. **HeadObject 대상 좁히기** (user_drive `resolveHeadableUrls`) — 이름 유출 차단
4. **쓰기 시점 소유 검증** 도입 (user_drive `assertNewAttachmentsOwnedBySelf`)
5. **왕복 동일성 검증** (user_drive `toStoredFilePath`) — ⚠️ 4번이 들어간 **뒤에야** 의미가 생긴다.
   왕복 검증의 본질은 "소유 검증을 우회하는 것을 막는" 것인데, 우회할 대상이 없으면 껍데기다

### 왜 PR #44 에 안 넣었나

주문접수는 쓰기 검증 자체가 없어서, 제대로 고치려면 PR #44 와 맞먹는 크기가 된다.
PR #44 는 이미 37커밋이고 리뷰 라운드가 4번 돌았다. 리스크 예산이 남지 않았다.

## 2. [중간] 첨부 저장 형식(콤마 조인)이 원천적으로 모호하다

### 무엇

첨부 목록을 컬럼 하나에 `join(',')` 로 저장하고 `parseFilePathList` 로 복원한다.
값(파일명) 안에 구분자가 들어갈 수 있어 **가역 직렬화가 아니다.**

PR #44 는 쓰기 시점 **왕복 동일성 검증**으로 "모호한 값이 새로 저장되는 것"을 막았을 뿐,
형식 자체는 그대로다. 같은 형식을 **5개 모듈이 공유**한다.

| 모듈 | 위치 | 왕복 검증 |
|---|---|---|
| user_drive | `user.drive.service.ts` (`toStoredFilePath`) | ✅ |
| order_receipt | `order.receipt.service.ts:261`, `:367` | ❌ |
| notice | `notice.service.ts:88`, `:115` | ❌ |
| qna | `qna.service.ts:225` | ❌ |
| inquiry | `inquiry.service.ts:96` | ❌ |

즉 **"검사 없이 join 하는 것"이 이 저장소의 기본값**이고 user_drive 만 예외다.

### 왜 지금 안 바꾸나

1. **파급 범위** — 테이블 5개 마이그레이션 + 백필 + 배포 중 구버전이 쓴 행에 대한 읽기 호환
2. **주문접수는 데이터 무결성까지 닿는다** — `auto.order.service.ts:207` 이
   `parseFilePathList(filePath).join('\n')` 의 SHA-256 을 자동주문 스냅샷 정합성 판정에 쓰고,
   `:139-150` 의 `fileIndexes`(파싱 결과의 **순서 인덱스**)를 멱등키로 쓴다.
   포맷을 바꾸면 기존 승인 건의 해시가 전부 어긋나고 멱등키 의미가 흔들린다 → **별도 설계 필요**
3. **연기 비용이 낮다** — API 계약은 이미 배열이라(`filePathList: string[]`) FE 재작업이 없고,
   왕복 검증이 새 모호 행을 막으므로 **부채가 커지지 않는 상태**다

### 방향 (JSON 컬럼보다 정규화가 낫다)

지금 `resolveHeadableUrls` 와 `assertDownloadable` 이 둘 다 **key 문자열을 split 해서 ownerId 를 역추출**한다
(`/^\d+$/` 정규식 검증까지 붙는다). 소유자를 **컬럼**으로 들고 있으면 이 파싱·검증이 통째로 사라진다.
JSON 컬럼은 모호성만 없애고 그 이득이 없다.

### 확인된 것 — 레거시 행 잠금 위험은 없다

`parseFilePathList` 는 입력을 항상 **분할(partition)** 하므로 `parseFilePathList(s)` 의 결과는
**항상 왕복 안전**하다(실측 10케이스, 이미 밀반입된 행 포함 전부 통과).
FE 가 `getDetail` 결과를 그대로 되보내는 정상 수정 플로우가 400 으로 잠기는 일은 발생할 수 없다.

## 3. [중간] 첨부 접근 권한 판정이 두 곳에 흩어져 있다

`user.drive.service.ts` 안에서 같은 도메인 규칙을 두 함수가 각각 구현한다.

| | `assertDownloadable` (다운로드) | `resolveHeadableUrls` (이름 노출) |
|---|---|---|
| 우리 버킷 아님 / key 파싱 실패 / ownerId 비숫자 | Forbidden | 대상 제외 |
| ownerId === senderId | 허용 | 대상 |
| 요청자가 관리자 | **우회 없음** | 분기 없음 |
| 업로더가 지금 SUPER | **안 본다**(조회 없음) | 안 본다 |

⚠️ **2026-08-18 정정.** 한때 이 표의 마지막 줄이 `무조건 허용` / *"의도된 차이"* 로 적혀 있었다.
그 관리자 우회는 리뷰 지적으로 **제거됐는데 문서만 옛 상태로 남아 있었다.** 그대로 두면 다음 사람이
이 문서를 근거로 우회를 되살린다(코드 주석은 정확히 그 반대를 경고하고 있었다).
**지금 두 판정의 객체 소유 규칙은 완전히 같다.** 그래서 아래 추출 리팩터의 명분도 그만큼 약해졌다
— 차이를 없애려는 게 아니라 중복을 줄이려는 것이다.

⚠️ **2026-08-21 재정정.** 위 표에 있던 *"업로더가 SUPER 면 허용"* 도 제거했다(리뷰 P1).
그건 첨부 당시의 사실이 아니라 **지금 바뀌는 값**이라, 같은 첨부가 승격·강등으로 보였다 안 보였다 했고
우회 쓰기로 남은 타인 소유 key 도 그 소유자가 SUPER 이기만 하면 열렸다.
**지금 두 함수의 판정은 `ownerId === senderId` 한 줄이고 DB 조회가 없다.**
`resolveHeadableUrls` 는 그래서 동기 함수가 됐다.

**후속 방향** — 판정이 한 줄로 줄어 추출의 명분이 더 약해졌다. 항목 2(정규화)로 소유자를 컬럼으로
들게 되면 두 함수의 ownerId 파싱이 통째로 사라지므로, **묶어서 진행하거나 그냥 두는 것**이 맞다.

## 3-b. [후속] SUPER 교차수정으로 '새 private 첨부' 를 넣는 흐름

위 판정을 한 줄로 좁히면서 **쓰기 시점 검증도 발신자(senderId) 기준**으로 맞췄다.
그래서 SUPER 가 남의 문서를 수정하며 **자기 계정으로 올린 새 private 첨부**를 넣으면 400 이다
(기존 첨부를 되보내는 것은 델타 검증이라 그대로 통과한다 — 정상 수정은 안 막힌다).

| | |
|---|---|
| **왜 이렇게 했나** | 그 흐름을 허용하려면 `ownerId ≠ senderId` 인 행이 생기고, 읽기 쪽이 그걸 열어 주려면 "업로더가 지금 SUPER 인가" 라는 **가변 판정**을 계속 들고 있어야 한다. 그게 리뷰 P1 의 실체였다 |
| **지금 깨지는 것** | 없다. 운영 실사에서 private 첨부 0건이고(§10), 프론트가 아직 `postFileImage`(→ `image/`)로 올려 공개 레거시 경로를 탄다 |
| **조용히 막히나** | 아니다. 등록 시점에 400 + 거절 로그(`등록: 발신자 소유가 아닌 private 첨부`)가 남는다 |
| **제대로 지원하려면** | ① 첨부자(업로더 id·시점 권한)를 문서 첨부 레코드에 저장하거나 ② SUPER 교차첨부 시 객체를 **발신자 네임스페이스로 복사**해 `ownerId === senderId` 불변식을 만든다. 둘 다 리뷰어가 제시한 선택지다 |
| **언제 필요해지나** | 프론트가 private 업로드로 전환한 뒤(FE 3단계), SUPER 가 교차수정으로 첨부를 넣는 운영 흐름이 실제로 쓰이면 |

## 4. [낮음] 로그 재귀에 깊이 상한이 없다

`src/common/api/logger.middleware.ts` 의 `maskSensitiveData` 는 요청 본문을 재귀 순회한다.
깊게 중첩된 JSON(실측: 60,000단 / 360KB)은 본문 상한(50mb)과 `JSON.parse` 를 통과하고
재귀에서 `RangeError` 를 낸다. 미들웨어는 가드보다 먼저 달리므로 **401 응답에도 해당**된다.

PR #44 에서 `res.on('finish')` 에 try/catch 를 넣어 **프로세스가 죽는 것은 막았다**
(그 전에는 `uncaughtException` → 워커 사망 → 그때 처리 중이던 다른 요청이 같이 죽었다).
근본 해결은 **재귀 깊이 상한**(예: 32 초과 시 `'[깊이초과]'`)이고, 이는 동작 변경이라 분리했다.

## 5. [낮음] 첨부 경로의 운영 관측 지점

PR #44 가 접근 로그에서 첨부 URL 을 쿼리·본문 양쪽에서 가렸다(`fileurl`/`filepath`/`filepathlist`).
같은 PR 에서 실패 경로에 `warn` 을 넣고 `maskStorageKeyForLog` 로 **원본명 없이 객체만 식별**되게 했다.

⚠️ **2026-08-18 보강.** 위 문장은 **S3 실패 경로에만** 참이었다. 정작 이 기능이 막으려는 것
(남의 private key 밀반입)은 **거절되면 400/403 으로 끝나고 앱 로그에 한 줄도 안 남았다.**
접근 로그의 `filePath` 마저 `***` 로 가려 놔서 "무슨 key 를 노렸나" 를 되짚을 방법이 0 이었다.
→ 쓰기·읽기 거절 지점 전부에 `warnAttachmentRejected` 를 넣었다(내부 id + 마스킹 key 만 남긴다).

남은 선택지 — **정상** 요청에도 상관키(예: key 의 SHA-256 앞 8자)를 남길 것인가.
지금은 실패·거절했을 때만 흔적이 남는다. 첨부 관련 CS 빈도를 보고 정할 것.
이 저장소에는 이미 *"값은 빼되 흔적은 남긴다"* 관례가 있다(`prepareForLogging` 이 비밀번호를 `hasPassword: true` 로).

## 6. [운영] 이미 저장된 밀반입 행 실사

PR #44 의 왕복 검증은 **쓰기 시점**이라 이미 저장된 행은 그대로 남는다.
읽기 쪽 방어(`assertDownloadable` + `resolveHeadableUrls`)로 노출은 좁혔지만, **몇 건인지는 안 세어봤다.**

⚠️ **깔끔한 SQL 탐지가 어렵다.** 정상 다중 첨부도 `,https://` 를 포함하므로 `LIKE` 로는 못 가른다.
판별 신호는 *"한 URL 의 pathname 안에 콤마가 있다"* 이고, 이건 앱 레벨에서 `parseFilePathList` 로
파싱한 뒤 각 URL 의 key 를 보는 일회성 스크립트가 현실적이다.

대상 테이블: `user_drive`, `order_receipt`, `notice`, `qna`, `inquiry` 의 `file_path`
(⚠️ `SnakeNamingStrategy` 라 코드의 `filePath` 는 DB 에서 `file_path` 다).

## 7. ✅ [해결됨 2026-08-18] S3 클라이언트에 타임아웃이 없다 — 상대가 멈추면 요청이 영영 안 끝난다

> **해결.** 다만 **처음 고친 방법이 틀려서 두 번 고쳤다.** 그 기록을 남긴다 — 안 적으면 다음 사람이 같은 함정을 밟는다.
>
> **1차 (틀림)** — `requestHandler: { connectionTimeout: 30_000, socketTimeout: 30_000 }`.
> `requestTimeout` 이 '총 시간' 이라 대용량 전송을 끊는다는 것까지는 맞게 갈랐는데,
> `socketTimeout` 이 본문 stall 을 막아 준다고 단정했다. **안 막는다.**
> `@smithy/node-http-handler` 는 값이 6000 이상이면 소켓 타임아웃 등록을 3초 미루고
> (`DEFER_EVENT_LISTENER_TIME = 3000`), 응답 **헤더** 가 도착하면 `resolve()` 가 `clearTimeouts()` 로
> 그 예약을 지운다. S3 가 정상이면 헤더는 1초 안에 오므로 **정상일수록 타임아웃이 아예 안 걸린다.**
>
> 그때 테스트는 *"옵션이 생성자에 전달됐는지"* 만 봐서 **뮤테이션까지 통과**했다.
> ⚠️ 뮤테이션은 "테스트가 코드를 지키나" 를 본다. **"코드가 증상을 막나" 는 안 본다.**
>
> **2차 (현재)** — `socketTimeout` 을 빼고 `downloadFileToLocalWithPath` 가 직접 잰다.
> `writeStream.bytesWritten` 이 30초 동안 안 늘면 `Body.destroy` 로 끊는다.
> (`Body` 에 `'data'` 리스너를 붙이는 방식은 안 쓴다 — flowing 모드로 바뀌어 pipeline 배선 전에 청크가 샌다.)
> `connectionTimeout` 은 남겼다 — 연결 수립 단계는 옵션만으로 실제 동작한다.
> 회귀를 **행동 기준**으로 다시 썼다: '한 청크 뒤 end 도 error 도 없이 멈추는 Readable' 로
> 매달림·부분파일·정상본문 오인 3케이스(`file.storage.s3.download.spec.ts`). 되돌리면 빨개진다.
>
> **교훈** — 남의 라이브러리 내부(타이머 등록 시점·이벤트 순서)에 안전을 걸면 버전만 올라가도 조용히 깨진다.
> 옵션으로 해결되는 것처럼 보여도 **그 방어가 막겠다는 증상을 한 번은 재현해 봐야 한다.**
>
> 아래는 왜 필요했는지의 기록이다.

`src/file/infra/file.storage.s3.ts:27-33` 의 `S3Client` 는 `requestHandler` 를 주지 않는다.
`@smithy/node-http-handler` 기본값은 **전부 무제한**이다(`connectionTimeout`·`requestTimeout`·
`socketTimeout` 모두 0 = 끔).

`pipeline` 은 스트림이 **끝나는** 경로만 덮는다. 상대가 데이터도 오류도 안 주고 멈추는 것(stall)은
끝나는 경로가 아니라서 안 덮인다 → `downloadFileToLocalWithPath` 의 Promise 가 settle 되지 않고
부분 임시파일·소켓·요청 컨텍스트가 무기한 남는다. 상세조회는 HeadObject 를 최대 10개 동시에 쏘므로
하나만 멈춰도 상세 전체가 안 끝난다. **오류 로그도 접근 로그도 안 남는다**(항목 8 참조).

- 타임아웃 부재 자체는 **develop 기존**이다. 다만 이번에 새 진입점 2개(프록시 다운로드 · 상세 HeadObject)가
  생겨 노출면이 넓어졌고, 주석이 "모든 종료 경로를 덮는다" 고 단언해 닫힌 것처럼 읽혔다(주석은 정정함).
- 값이 판단 사항이라 한 번 미뤘었다 — 같은 클라이언트를 대용량 업로드/다운로드(20MB 상한)와
  엑셀 파싱(`getBuffer`)이 함께 쓴다. 지금 방식이 그걸 안 깨는 이유는 **무응답 기준**이기 때문이다.
  데이터가 흐르는 동안에는 아무리 오래 걸려도 안 걸린다.
- `@smithy/node-http-handler` 를 직접 import 하지 않았다 — 선언 안 된 전이 의존성이라서.
  `NodeHttpHandler.create(config?.requestHandler)` 가 평범한 객체도 받는다(`client-s3/runtimeConfig.js:49`).

## 8. [중간] 중단·실패한 다운로드는 접근 로그에 줄이 아예 안 남는다

`src/common/api/logger.middleware.ts` 는 `res.on('finish')` 에서 로그를 쓴다.
`finish` 는 `res.end()` 가 완료돼야 뜬다. 스트림 오류나 클라이언트 중단으로 `res` 가 destroy 되면
**`close` 만 뜨고 `finish` 는 안 뜬다**(실측 확인). 그러면 그 요청은 접근 로그에 **줄 자체가 없다.**

- 400/403 거절은 정상 응답이라 로그가 남는다 → 항목 5 와는 다른 구멍이다.
- 미들웨어 구조는 **develop 기존**이다. 다만 이번에 **중단이 정상인 엔드포인트(대용량 스트리밍)** 를
  처음 들여서 비로소 문제가 된다.
- 고치려면 `close` 를 듣고 1회만 남기게 바꿔야 하는데, 이건 **전 저장소 접근 로그의 동작 변경**이라
  이 PR 범위 밖으로 뒀다.

## 9. ✅ [해결됨 2026-08-18] 스트리밍 실패 시 500 JSON 은 사실상 안 나간다

> **해결(문서함 한정).** 원인이 둘이었는데 하나만 보고 "후속" 으로 미뤘었다.
> ① pipeline 이 오류 시 `res` 를 destroy 한다 (원래 적어둔 것)
> ② **`fs.createReadStream` 은 파일을 동기로 열지 않는다** — try/catch 는 동기 throw 만 잡고,
>    비동기 open 실패(EMFILE·EACCES·ENOENT)는 이미 헤더를 건 뒤에 온다 (못 봤던 축)
>
> `user.drive.controller.ts` 가 **open 을 기다린 뒤 헤더를 걸도록** 바꿨다. 전송 시작 전 실패는
> 헤더 없는 예외로 나가 ExceptionFilter 가 500 JSON 을 만든다. 실패 경로에서 스트림 destroy + 임시파일 정리.
> 컨트롤러 스펙 3케이스 신설 — 이 저장소에 컨트롤러 레벨 테스트가 0건이라 헤더 시점·임시파일·실패 모양이
> 통째로 미검증이었다.
>
> ✅ **형제(`order_receipt`)도 같이 고쳤다(2026-08-21).** 같은 구조였고, 오히려 헤더를
> `createReadStream` 보다도 먼저 걸고 있었다. 컨트롤러 스펙 3케이스도 함께 신설했다.
> 아래는 원래 기록이다.

`user.drive.controller.ts` 와 `order.receipt.controller.ts` 는 pipeline 콜백에서
`if (!res.headersSent && !res.destroyed)` 일 때 500 JSON 을 쓴다. 그런데 **`pipeline` 은 오류 시 모든
스트림을 destroy** 하므로 여기 올 때는 `res.destroyed` 가 이미 참이다.

실측(Node v24, 실제 http 서버): `headersSent=false / destroyed=true / 클라이언트는 ECONNRESET`.
→ 사용자는 JSON 이 아니라 브라우저의 "다운로드 실패" 를 본다. **원인을 아는 유일한 창구는 error 로그다.**

주석은 사실대로 정정했다(양쪽 컨트롤러). 실제로 JSON 을 주려면 pipeline 앞에서 소스 오류를 먼저
받아야 하는데, 그건 동작 변경이고 형제 컨트롤러와 같이 가야 해서 미뤘다.

## 10. ✅ [해결됨 2026-08-18] 관리자 우회 제거의 과차단 실사

> **운영에서 셌고 0건이다. 배포를 막을 것이 없다.**
> `private_담긴_문서 = 0` (첨부 있는 문서 48건 전수). 바뀐 판정은 `private/` 분기 안에만 있으므로
> `private/` key 가 하나도 없으면 과차단은 원리상 생길 수 없다.
> 배포 순서가 BE 먼저라 배포 시점까지 private 첨부가 새로 생길 경로도 없다(프론트는 아직
> `postFileImage` → `image/` 로 올린다). 아래는 어떻게 셌는지의 기록이다.

`assertDownloadable` 에서 "요청자가 관리자면 소유검사 생략" 을 제거했다. 새로 저장되는 첨부는
쓰기 검증이 `ownerId === 등록자` 를 강제하므로 과차단이 생길 수 없다.

⚠️ **문제는 그 이전에 저장된 행이다.** `ownerId ≠ senderId` 이면서 업로더가 SUPER 도 아닌 첨부가
남아 있으면, **전에는 관리자가 받을 수 있던 것이 이제 403** 이 된다.

**배포 전에 세야 한다.** 0건이면 그냥 배포, 0건이 아니면 그 문서들을 어떻게 할지 먼저 정해야 한다.

### 먼저 이 SQL 한 줄로 갈린다

바뀐 판정은 **`private/` 분기 안에만** 있다(레거시 `image/`·`file/` 는 그 위에서 그냥 통과한다).
그래서 `private/` key 가 아예 없으면 과차단은 원리상 생길 수 없다.

```sql
SELECT COUNT(*)                         AS 문서_전체,
       SUM(file_path LIKE '%private/%') AS private_담긴_문서
FROM user_drive
WHERE deleted_at IS NULL AND file_path IS NOT NULL;
```

`private_담긴_문서 = 0` 이면 **끝이다.** 0 이 아닐 때만 아래 스크립트로 들어간다.

### 0 이 아니면 — 파싱이 필요하다

SQL 만으로는 못 가른다. 저장이 콤마 조인이라 URL 경계 판단이 필요하고(파일명에 콤마가 들어갈 수 있어
단순 split 이 틀린다), key 에서 뽑은 ownerId 를 `user.authority` 와 맞춰봐야 한다.
그래서 **운영 코드의 `parseFilePathList` 를 그대로 쓰는** 일회성 스크립트를 만들어 뒀다.
규칙을 다시 구현하면 결과가 갈리므로 원본 함수를 재사용한다.

```
sql/ops/audit-user-drive-attachment-owner.ts   (읽기 전용 · git 미추적)
npx ts-node -r dotenv/config sql/ops/audit-user-drive-attachment-owner.ts
```

접속 정보는 `.env` 의 `DATABASE_*` 를 쓴다. 다른 DB 를 보려면 `DOTENV_CONFIG_PATH` 로 바꾼다.

### 실측 (2026-08-18)

| 대상 | 결과 | 누가 |
|---|---|---|
| **개발 DB** | 첨부 있는 문서 56 · 첨부 78개 · **private 0 / 레거시 `image/` 78** → 과차단 **0건** | 스크립트 + SQL 둘 다 (대조군 일치) |
| **운영 DB** | 첨부 있는 문서 48 · **private 담긴 문서 0** → 과차단 **0건** | 위 SQL (운영자 실행) |

private 이 0 인 건 놀랍지 않다 — 프론트가 아직 `postFileImage`(→ `image/`)로 올리므로 문서함에
private 첨부가 생길 경로가 없다. 그래도 개발이 0 이라고 운영이 0 인 건 아니라서 따로 셌다.

⚠️ **이 결론이 성립하는 전제** — "바뀐 판정이 `private/` 분기 안에만 있다" 는 것.
`assertDownloadable` 의 다른 분기(우리 버킷 아님 · key 파싱 실패 · 허용되지 않은 위치)는 이번에
동작이 안 바뀌었다. 그 분기를 나중에 손대면 이 실사는 다시 해야 한다.
