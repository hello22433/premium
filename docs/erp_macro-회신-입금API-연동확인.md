## 0. 한 줄 요약

**명세와 프리미엄 구현 사이에 어긋나는 곳이 없습니다.** 명세 §10의 확인 요청 3건 중
프리미엄이 답할 수 있는 2건은 아래에 답했고, 남은 1건(키 발급)은 그쪽 액션입니다.

## 1. §10-② "가장 중요" — null 되돌림: **덮어씁니다** ✅

> 질문: *ECOUNT 에서 거래처를 떼거나 회계반영을 취소하면 `erpPartnerName` / `erpPartnerCode` /
> `voucherNo` 가 null 로 전달된다. 프리미엄 upsert 가 이 필드들을 null 로도 덮어쓰는가?*

**덮어씁니다. coalesce(값이 있을 때만 갱신) 하지 않습니다.** 원하시는 동작 그대로입니다.

실제 MySQL에 붙여 실증했습니다(일회용 DB 생성 → 검증 → 삭제하는 스모크 스크립트):

```
PASS  원본이 voucher_no 를 되돌리면 미러도 null 이 된다     null
PASS  원본이 거래처를 떼면 미러도 null 이 된다              {"name":null,"code":null}
PASS  되돌림 동기화에도 운영자 매칭은 여전히 보존된다        보존됨
```

**세 번째 줄이 함께 성립하는 것이 중요합니다.** 프리미엄 미러 테이블은 컬럼 소유권이 둘로 갈립니다.

| 컬럼 부류 | 동기화 동작 |
|---|---|
| 원본 미러 컬럼 (그쪽이 정본) | **null 로도 덮어쓴다** — 거울로 유지 |
| 프리미엄 소유 컬럼 (매칭 상태) | **건드리지 않는다** |

`ON DUPLICATE KEY UPDATE` 의 갱신 컬럼을 명시적으로 열거하는 방식이라, "원본은 그대로 따라가되
운영자가 지정한 매칭은 살아남는" 두 성질이 동시에 성립합니다.

## 2. §10-③ size 상한 — 500 사용, 조정 불필요 ✅

- 프리미엄 사용값: **500** (그쪽 상한 2000 이내, 통과 확인)
- 프리미엄 자체 상한: 1000 (더 보수적. 실사용이 500이라 동작 영향 없음)

**상한 유지에 동의합니다.** 다만 한 가지 부탁이 있습니다.

> ⚠️ **요청한 `size` 를 서버가 말없이 깎지 말아 주세요.**
> 프리미엄의 페이지 순회 종료 조건이 `받은 개수 < 요청 개수` 입니다. 요청 500에 대해 서버가
> 200으로 깎아 돌려주면 첫 페이지부터 종료 조건이 참이 되어 **한 페이지만 읽고 멈춥니다.**
> 에러가 없어서 눈에 띄지 않는 종류의 사고입니다. 상한 초과 시에는 깎기보다 **400** 이
> 프리미엄 입장에서 안전합니다(즉시 중단 + 에러 로그로 사람이 봅니다).
> 현재 500은 상한 안이라 문제 없고, **상한을 500 아래로 낮출 계획이 생기면 사전에 알려주세요.**

## 3. §10-① base URL · API 키 — **그쪽 액션 대기** ⬜

프리미엄은 아래 env 4개로 받을 준비가 되어 있습니다. 값이 없으면 동기화는 **꺼진 채로** 뜨고
조회 화면은 정상 동작합니다(빈 미러를 읽음).

```
ERP_MACRO_API_BASE_URL=https://<스크래핑 서버>
ERP_MACRO_API_KEY=<발급 키>
DEPOSIT_SYNC_ENABLED=false   # 도달 확인 후 true
```

- 운영·개발 **각각** 필요합니다.
- 키는 저장소에 커밋하지 않고 환경변수/SSM 으로 주입합니다.
- erp_macro 인바운드 IP 허용목록에 넣을 **프리미엄 서버 IP** 는 별도로 전달드리겠습니다.

## 4. 프리미엄 구현이 명세를 따르고 있음 (대조 결과)

| 명세 항목 | 프리미엄 구현 |
|---|---|
| `page` 0-based | ✅ 0부터 시작 |
| `sort` 를 `txDate,asc` + `id,asc` 두 번 전달 | ✅ (배열 직렬화가 아니라 같은 키를 두 번 보냄) |
| 응답 봉투 5키 | ✅ `content`(배열), `totalElements`(number) 만 사용 |
| `txDate` 는 타임존 없는 날짜 | ✅ 문자열로 취급. `Date` 로 변환하지 않음 |
| `scrapedAt` UTC(Z) | ✅ 저장, 화면 표시 시 KST 변환 |
| `dedupKey` 기준 멱등 upsert | ✅ UNIQUE 인덱스 + 명시적 갱신 컬럼 |
| 401 / 400 / 404 → 즉시 중단 | ✅ 영구 실패로 분류, **error** 로그 |
| 5xx / timeout → 다음 주기 재시도 | ✅ 일시 실패로 분류, **warn** 로그 |
| 200 인데 `content` 없음 → 일시 실패 | ✅ 동일 처리 |
| 5분 주기 / 최근 30일 통째 재요청 | ✅ |

`amount`/`balance` 는 BIGINT 로 받아 문자열로 저장합니다(JS 정수 정밀도 문제 회피).
`txType` 한글 원문(`입금`/`출금`)은 그대로 보존하고, 영문 변환은 프리미엄 화면에서만 합니다.

## 5. 프리미엄이 추가로 알리는 것 (그쪽 작업 불필요)

### 5-1. 미러도 PII 를 암호화 저장합니다

그쪽이 자기 DB에 암호화 보관하는 4종(`depositor` / `depositorRaw` / `erpPartnerName` /
`erpPartnerCode`)을 **프리미엄 미러도 암호화해서 저장**합니다. 사본이 원본보다 보호 수준이
낮으면 미러를 두는 것 자체가 전체 보안 등급을 낮추는 일이 되기 때문입니다.

**API 응답 형식에는 영향이 없습니다** — 지금처럼 평문으로 주시면 됩니다.

### 5-2. 입금처 검색 시 감사 로그를 남깁니다

예금주 실명으로 검색하면 프리미엄 `activity_log` 에 `PII_SEARCH` 를 기록합니다(검색어는
마스킹). 결과가 0건이어도 남깁니다. 그쪽 작업은 없습니다.

### 5-3. 데이터 최대 지연은 8분입니다

```
ECOUNT → erp_macro 폴링 3분 → premium pull 5분  =  최대 8분
```

정상 동작이며, 프리미엄 화면에 "최근 수집 시각"을 노출해 운영자가 오해하지 않도록 합니다.
`GET /api/status` 가 그 표시의 근거입니다.

### 5-4. `gateTripped=true` 여도 프리미엄은 계속 호출합니다

게이트가 걸려 그쪽 수집이 멈춰도 프리미엄은 5분마다 계속 당깁니다. 새 데이터가 없을 뿐이고,
게이트가 풀리면 자동으로 따라잡습니다. **화면에는 `gateTripped` / `gateReason` 을 그대로
노출해 운영자가 개입 필요를 알 수 있게 합니다.**

## 6. 변경 시 반드시 사전 협의가 필요한 것 — 딱 하나

> ### ⚠️ `dedupKey` 산식과 정규화 규칙
>
> - 산식: `SHA-256(계좌 | 일자 | 구분 | 금액 | 잔액 | 입금처)`
> - 정규화: 입금처 `(가상)` 접두 제거 + 앞뒤 trim
> - `voucherNo` 제외
>
> 이게 바뀌면 **같은 거래가 새 지문으로 들어와 프리미엄에 같은 입금이 두 줄** 생깁니다.
> 자동으로 감지할 방법이 없고, 발견 시점에는 이미 중복이 쌓여 있습니다.
> 정규화 규칙도 계약의 일부입니다(공백 처리 하나만 바뀌어도 전 건의 지문이 달라집니다).

나머지(필드 추가, 봉투 키 추가, 정렬 기본값 변경 등)는 프리미엄이 모르는 값을 무시하도록
되어 있어 사전 협의 없이 바꾸셔도 깨지지 않습니다.
