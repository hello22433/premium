# API 계약 — erp_macro 입금내역 조회 (프리미엄이 호출)

> **누가 누구를 부르나:** 프리미엄(AWS)이 erp_macro(스크래핑 서버)를 **주기적으로 호출(pull)** 해서
> 입금 거래내역을 받아 자기 DB에 미러링한다. erp_macro 는 요청을 받아 돌려주기만 한다.
>
> **역할 분리:** erp_macro = "ECOUNT 데이터 제공자"(긁고, 저장하고, 준다).
> 고객 매칭·입금처 매핑·예치금 충전은 **전부 프리미엄** 소유이며, 이 API 에 등장하지 않는다.

---

## 0. 왜 프리미엄이 사본을 갖는가

프리미엄은 받은 데이터를 자기 DB(`epopkon.bank_deposit`)에 **미러링**한다. 화면은 그 미러를 읽는다.
실시간으로 매번 erp_macro 를 호출하지 않는 이유는 셋이다.

1. **매칭 상태는 프리미엄만 안다.** "미매칭만 골라 3페이지"를 erp_macro 는 계산해 줄 수 없다.
   필터·정렬·페이징이 두 시스템에 갈리면 서버 페이징이 성립하지 않는다.
2. **가용성.** 스크래핑 서버가 꺼져 있어도 조회 화면은 떠야 한다.
3. **응답 속도.** 화면이 사무실 회선 왕복에 묶이지 않는다.

그래서 이 API 는 **화면이 직접 부르는 API 가 아니라, 동기화 배치가 부르는 API** 다.
사람이 기다리지 않으므로 응답이 다소 느려도 되고, 대신 **빠짐이 없어야** 한다.

---

## 1. 엔드포인트

### 1-1. 거래내역 조회

```
GET {BASE_URL}/api/deposits?from=2026-07-01&to=2026-07-31&page=1&size=500
X-API-KEY: <발급된 키>
```

| 파라미터 | 필수 | 형식 | 의미 |
|---|---|---|---|
| `from` | ✅ | `yyyy-MM-dd` | 거래일자 시작 (**해당일 포함**) |
| `to` | ✅ | `yyyy-MM-dd` | 거래일자 종료 (**해당일 포함**) |
| `page` | | 1부터 | 기본 1 |
| `size` | | 1~1000 | 기본 500 |

**정렬은 서버가 `tx_date ASC, id ASC` 로 고정한다.** 클라이언트가 정렬을 고르지 않는다.
페이지를 넘겨가며 읽는 동안 순서가 흔들리면 행이 중복되거나 새는데, 유일값(`id`)을
마지막 정렬 키로 고정해야 그게 막힌다.

### 1-2. 수집 상태 조회 ⭐ (빠뜨리면 안 되는 것)

```
GET {BASE_URL}/api/status
X-API-KEY: <발급된 키>
```

```json
{
  "lastScrapedAt": "2026-08-03T10:35:51.995+09:00",
  "gateTripped": false,
  "gateReason": null
}
```

| 필드 | 의미 |
|---|---|
| `lastScrapedAt` | 마지막으로 스크래핑에 **성공한** 시각 |
| `gateTripped` | 스크래퍼 차단기(`deposit_polling_gate`) 작동 여부. `true` 면 수집이 멈춰 있음 |
| `gateReason` | 차단 사유 (로그인 실패, 기기 재등록 필요 등) |

**왜 필요한가:** pull 방식에서 데이터가 안 늘어날 때, 그게 *"오늘 입금이 없었다"* 인지
*"스크래퍼가 죽었다"* 인지 프리미엄은 구분할 수 없다. 돈 관련 화면에서 이 둘을 혼동하면
"입금이 안 들어왔다"는 잘못된 판단으로 이어진다. 프리미엄은 이 값을 받아 화면에
"수집이 N시간째 멈춰 있습니다" 경고를 띄운다.

## 2. 응답 형식

```json
{
  "items": [
    {
      "dedupKey": "f57b73d0f18abfd24fdbdb469ba5e21ea1f500919098801c57ded5881f481cd5",
      "txDate": "2026-07-29",
      "txType": "입금",
      "accountNo": "280***01757104",
      "accountName": "(주)모바일이앤엠애드",
      "erpPartnerCode": null,
      "erpPartnerName": null,
      "depositor": "두성종이",
      "depositorRaw": "(가상)  두성종이",
      "amount": 350000,
      "balance": 45717465,
      "voucherNo": "2026/07/29-2",
      "scrapedAt": "2026-08-03T10:35:51.995+09:00",
      "updatedAt": "2026-08-03T10:35:52.479+09:00"
    }
  ],
  "page": 1,
  "size": 500,
  "totalCount": 4837
}
```

### 필드 규약

| 필드 | 타입 | null | 규약 |
|---|---|---|---|
| `dedupKey` | string(64) | ❌ | **프리미엄의 멱등 키.** 아래 3장 참고 |
| `txDate` | string | ❌ | ⚠️ **날짜만.** `"2026-07-29"` — 시각·타임존을 붙이지 말 것 |
| `txType` | string | ❌ | ECOUNT 원문 그대로 (`입금`/`출금`). 영문 변환은 프리미엄이 함 |
| `accountNo` | string(50) | ❌ | 마스킹형 그대로 |
| `accountName` | string(100) | ✅ | ECOUNT 표기 그대로 |
| `erpPartnerCode` | string(50) | ✅ | |
| `erpPartnerName` | string(191) | ✅ | |
| `depositor` | string(191) | ❌ | `(가상)` 접두 제거본 |
| `depositorRaw` | string(191) | ✅ | 원문 |
| `amount` | number | ❌ | 원 단위 정수. JSON number 로 (원화는 안전 정수 범위 내) |
| `balance` | number | ❌ | 거래후 잔액 |
| `voucherNo` | string(50) | ✅ | ⚠️ 숫자가 아닐 수 있음 (`강제회계반영` 등 실측). 문자열 그대로 |
| `scrapedAt` | string | ❌ | ISO 8601 + **오프셋 필수** |
| `updatedAt` | string | ❌ | ISO 8601 + **오프셋 필수** |

### ⚠️ `txDate` 를 날짜 문자열로 고정하는 이유

`"2026-07-29T00:00:00Z"` 같은 시각 형태로 주면, 받는 쪽 타임존에 따라 **하루가 밀린다.**
실제로 프리미엄 로컬에서 재현했다 — DB 의 `2025-06-23` 이 드라이버를 거치며
`2025-06-22T15:00:00.000Z` 가 되고, 앞 10자를 자르면 `06-22` 가 된다.

거래일자는 "그 날"이라는 사실이지 특정 순간이 아니므로, 시각을 붙이는 순간 없던 문제가 생긴다.
`scrapedAt`/`updatedAt` 은 반대로 진짜 시각이므로 **오프셋을 반드시 붙여야** 한다.

### 이 API 에 없어야 하는 것

- `matchedUserId`, `matchStatus` — 프리미엄 소유. erp_macro 는 매칭을 하지 않는다
- `depositorMapping` 관련 일체 — 프리미엄으로 이동

## 3. 멱등성 — `dedupKey` 가 계약의 핵심

프리미엄은 받은 행을 `dedupKey` 기준으로 **upsert** 한다. 그래서:

- **같은 건이 여러 번 와도 안전하다.** 프리미엄은 매 주기 최근 구간을 통째로 다시 요청한다.
  중복 수신은 오류가 아니라 정상이며, 오히려 빠짐을 메우는 안전장치다.
- **`dedupKey` 는 절대 바뀌면 안 된다.** 같은 거래가 어제와 오늘 다른 지문으로 오면
  프리미엄에 **같은 입금이 두 줄** 생긴다. 회계 반영으로 `voucherNo` 가 나중에 채워져도
  지문이 안 바뀌도록 되어 있는 현재 설계(지문 = 계좌\|일자\|구분\|금액\|잔액\|입금처)를 유지할 것.
- 지문 산식을 바꿔야 한다면 **반드시 사전 협의**. 프리미엄 쪽 재매핑이 필요하다.

## 4. 프리미엄의 호출 패턴 (erp_macro 가 예상해야 할 부하)

| 항목 | 값 |
|---|---|
| 주기 | 5분 (`DEPOSIT_SYNC_CRON` 으로 조정) |
| 범위 | 매번 **최근 30일** 을 통째로 재요청 (기본값, 조정 가능) |
| 건수 | 30일 ≈ 500건 내외 → 요청 1~2회 |
| 최초 백필 | 전체 기간 1회 (약 4,900건 → 10회 내외) |

**왜 매번 최근 30일을 다시 받나:** `updatedAt` 기준 증분만 받으면 경계 시각 처리·시계 오차에서
빠짐이 생길 수 있다. 멱등 upsert 가 있으므로 통째로 다시 받는 쪽이 단순하고 안전하며,
이 데이터 규모(하루 수십 건)에서는 비용도 무시할 만하다. 규모가 커지면 `updatedSince`
파라미터를 추가하는 것으로 확장한다.

## 5. 보안

| 항목 | 요구 |
|---|---|
| 전송 | **HTTPS 필수.** 예금주 실명 + 금액이 오간다. 평문 HTTP 불가 |
| 인증 | `X-API-KEY` 헤더. 키 불일치 시 **401** |
| 출처 제한 | erp_macro 쪽에서 **프리미엄 서버 IP 만** 인바운드 허용 |
| 노출 범위 | 이 두 엔드포인트 외에는 인터넷에 열지 말 것 |

> 스크래핑 서버에는 ECOUNT 로그인이 통과된 브라우저 프로필이 남아 있다. 그 서버가 뚫리면
> 입금내역뿐 아니라 회계 시스템 접근까지 함께 넘어가므로, 열어 주는 표면을 최소로 잡는다.

---

## 6. 에러 규약

| 상황 | 상태 코드 | 프리미엄의 대응 |
|---|---|---|
| 키 불일치/누락 | 401 | 즉시 중단 + 에러 로그 (재시도해도 소용없음) |
| 파라미터 오류 | 400 | 즉시 중단 + 에러 로그 |
| 서버 오류·타임아웃 | 5xx / timeout | 이번 주기 포기, **다음 주기에 재시도** (멱등이라 안전) |

프리미엄은 실패를 조용히 삼키지 않고 로그로 남긴다. 부분 실패해도 다음 주기가 같은 구간을
다시 요청하므로 데이터는 자연히 수렴한다.

---

## 7. 프리미엄 쪽 설정 (참고)

```
ERP_MACRO_API_BASE_URL=https://<스크래핑 서버 주소>
ERP_MACRO_API_KEY=<발급 키>
DEPOSIT_SYNC_ENABLED=false        # 상대 API 준비 전까지 꺼둠
DEPOSIT_SYNC_RESYNC_DAYS=30
```
