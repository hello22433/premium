# API 계약 — erp_macro 입금내역 조회 (프리미엄이 호출)

> **정본은 이 문서가 아니라 상대 구현이다.** 2026-08-05 상대 통합 명세(`erp_macro 입금 API —
> 프리미엄 최종 연동 명세`)와 대조해 갱신했다. 근거 파일:
> - `api/DepositController.java`, `api/StatusController.java`, `api/DepositView.java`
> - `api/PageResponse.java`, `deposit/DepositFingerprint.java`, `config/ApiKeyAuthFilter.java`
>
> **⚠️ 응답 봉투가 Spring `Page` 가 아니라 전용 DTO(`PageResponse`) 로 확정됐다.**
> `content` / `number` / `size` / `totalElements` / `totalPages` **5개 키만** 담으며 Spring 버전
> 업글에도 형태가 안 바뀐다. 프리미엄은 이 중 `content`(배열)와 `totalElements`(number)만 읽고
> 나머지는 쓰지 않으므로, 키가 늘거나 줄어도 영향받지 않는다.
>
> **누가 누구를 부르나:** 프리미엄(AWS)이 erp_macro(스크래핑 서버)를 5분마다 호출(pull)해
> 자기 미러 테이블에 적재한다. 화면은 미러를 읽는다.
>
> **역할 분리:** erp_macro = "ECOUNT 데이터 제공자". 고객 매칭·입금처 매핑·예치금 충전은
> 전부 프리미엄 소유이며 이 API 에 등장하지 않는다.

---

## 0. 프리미엄이 사본(미러)을 두는 이유

프리미엄은 받은 데이터를 자기 DB(`epopkon.bank_deposit`)에 미러링하고, 화면은 그 미러를 읽는다.
화면이 이 API 를 실시간으로 호출하지 않는 이유는 넷이다.

1. **매칭 상태는 프리미엄만 안다.** "미매칭만 골라 3페이지"를 erp_macro 는 계산해 줄 수 없다.
   필터·정렬·페이징이 두 시스템에 갈리면 서버 페이징이 성립하지 않는다.
2. **입금처 부분검색이 API 에 없다.** depositor 가 암호화 저장이라 상대가 LIKE 를 못 건다.
   화면의 입금처 검색은 미러에서만 가능하다.
3. **가용성.** 스크래핑 서버가 꺼져 있어도 조회 화면은 떠야 한다.
4. **응답 속도.** 화면이 스크래핑 서버 회선 왕복에 묶이지 않는다.

> 참고: 요청 스펙에 "프리미엄 DB 에 아무 테이블도 만들지 않는다"는 문장이 있으나, 같은 문서
> §3 이 "입금처→고객 학습 매핑 테이블은 프리미엄 쪽에 둔다"고 하므로 그 문장은 *"erp_macro 가
> 프리미엄 DB 에 write 하지 않는다"* 로 읽는 것이 맞다. 프리미엄이 자기 소유 테이블을 갖는 것은
> 그 분리를 깨지 않는다.

## 1. 현행 구현 (확정)

### 1-1. 거래내역 조회

```
GET {BASE_URL}/api/deposits?from=2026-07-01&to=2026-07-31&page=0&size=500&sort=txDate,asc&sort=id,asc
X-API-KEY: <발급된 키>
```

| 파라미터 | 필수 | 형식 | 비고 |
|---|---|---|---|
| `from` / `to` | 선택 | `yyyy-MM-dd` | 거래일자 범위(해당일 포함) |
| `txType` | 선택 | `입금` / `출금` | **ECOUNT 한글 원문**. 프리미엄은 미러에서 거르므로 사용하지 않음 |
| `account` | 선택 | 마스킹형 계좌번호 | 정확일치 |
| `page` | 선택 | ⚠️ **0-based** | Spring Pageable. 첫 페이지가 **0** |
| `size` | 선택 | 기본 50 | 프리미엄은 500 사용 |
| `sort` | 선택 | `txDate,asc` `id,asc` | 아래 참고 — 프리미엄은 항상 명시해 보낸다 |

**⚠️ 정렬을 오름차순으로 명시해 보내는 이유**

상대 기본값은 최신순(`txDate,id DESC`)이다. 그런데 페이지를 넘겨가며 읽는 도중 새 거래가
들어오면, 내림차순에서는 새 행이 **맨 앞에 끼어들어** 뒤 페이지가 한 칸씩 밀린다. 그러면
아직 읽지 않은 행이 이미 지나간 페이지 쪽으로 이동해 **영구 누락**된다. 최초 백필은 90+
페이지를 도는데 스크래핑 주기가 3분이므로 그 사이 새 행이 들어오는 것은 확실하다.

오름차순이면 새 행은 항상 **끝에 붙으므로** 순회가 안전하다. Spring 은 요청의 `sort` 가
`@PageableDefault` 를 덮으므로 프리미엄이 명시한다. (상대 기본값 변경은 요청하지 않는다 —
화면용 소비자에게는 최신순 기본값이 자연스럽다)

### 1-2. 응답 — Spring Data `Page`

```json
{
  "content": [
    {
      "id": 4712,
      "dedupKey": "b482ecfb047f...(64자)",
      "txDate": "2026-08-04",
      "txType": "입금",
      "accountNo": "131***40301018",
      "accountName": "기업은행",
      "depositor": "두성종이",
      "erpPartnerName": "두성종이(주)",
      "amount": 350000,
      "balance": 12345678,
      "voucherNo": null,
      "scrapedAt": "2026-08-04T05:47:00.123456Z"
    }
  ],
  "totalElements": 4652,
  "totalPages": 94,
  "number": 0,
  "size": 50
}
```

| 필드 | 타입 | null | 규약 |
|---|---|---|---|
| `id` | number | ❌ | erp_macro 행 id. 프리미엄은 `dedupKey` 를 키로 쓰므로 참고용 |
| `dedupKey` | string(64) | ❌ | **프리미엄의 멱등 키.** 3장 참고 |
| `txDate` | string | ❌ | Java `LocalDate` → `"2026-08-04"`. 시각·타임존 없음 |
| `txType` | string | ❌ | ECOUNT 원문(`입금`/`출금`). 영문 변환은 프리미엄이 함 |
| `accountNo` | string | ❌ | 마스킹형 |
| `accountName` | string | ✅ | ECOUNT 표기 그대로 |
| `depositor` | string | ❌ | 예금주명 평문(상대 DB 에선 암호화, 응답 시 복호) |
| `erpPartnerName` | string | ✅ | |
| `amount` / `balance` | number | ❌ | 원 단위 정수(Java `long`) |
| `voucherNo` | string | ✅ | ⚠️ 숫자가 아닐 수 있음(`강제회계반영` 등 실측). 파싱 금지 |
| `scrapedAt` | string | ❌ | Java `Instant`(UTC `Z`). ⚠️ **최초 목격 시각**이며 재스크래핑으로 갱신되지 않음 |

### ⚠️ `txDate` 가 날짜 문자열인 것이 중요한 이유

시각 형태(`2026-07-29T00:00:00Z`)로 오면 받는 쪽 타임존에서 **하루가 밀린다.** 프리미엄
로컬에서 재현했다 — DB 의 `2025-06-23` 이 드라이버를 거쳐 `2025-06-22T15:00:00.000Z` 가 되고,
앞 10자를 자르면 `06-22` 다. 현재 `LocalDate` 로 직렬화되고 있어 문제없다. **바꾸지 말 것.**

## 2. 프리미엄이 요청했던 보완 3건 — **①② 반영 완료 (2026-08-05)**

| | 요청 | 결과 |
|---|---|---|
| ① | `GET /api/status` 신설 | ✅ **구현됨.** 요청안보다 나은 형태 — `pollingEnabled` 가 추가됐다 |
| ② | `depositorRaw` / `erpPartnerCode` 추가 | ✅ **구현됨.** 둘 다 응답에 있음 |
| ③ | 원본 변경 시각 | ❌ 미도입. 선택 사항이었고 **필요 없다** (아래) |

③이 필요 없는 이유: 프리미엄이 매 주기 최근 30일을 통째로 다시 받으므로 원본 변경은 자연히
반영된다. `scrapedAt` 은 여전히 "최초 목격 시각"이며 재스크랩으로 갱신되지 않는다 —
**"원본이 마지막으로 바뀐 시각"으로 해석하면 안 된다.**

> `pollingEnabled` 는 프리미엄이 요청하지 않은 값인데 상대가 넣었다. `lastScrapedAt=null` 이
> "폴링이 꺼진 것"인지 "켜져 있는데 아직 첫 성공 전"인지 가른다. 프리미엄은 이 값이 없는 응답도
> 처리한다(`?? null` → 화면에서 "꺼짐"이 아니라 **"모름"** 으로 읽어야 한다).

### ① `GET /api/status` 신설 (권장)

두 값 모두 **erp_macro DB 에는 이미 있고**(`20260722_create_deposit_recon_tables.sql`),

- `depositorRaw` — `(가상)` 접두를 포함한 원문. 화면 툴팁·감사 대조용
- `erpPartnerCode` — ECOUNT 거래처코드. 매칭 초기값 힌트로 쓸 수 있음

없으면 프리미엄은 `null` 로 저장한다(추가되는 날 코드 변경 없이 자동 반영).

프리미엄이 매 주기 최근 30일을 통째로 다시 받으므로 변경은 자연히 반영된다.

## 2-B. 상대의 확인 요청 — **null 되돌림 (회신 완료)**

> 상대 명세 §6: *"ECOUNT 에서 거래처를 떼거나 회계반영을 취소하면 `erpPartnerName` /
> `erpPartnerCode` / `voucherNo` 가 null 로 바뀌어 전달된다. 프리미엄 upsert 가 이 필드들을
> **null 로도 덮어쓰는지** 봐 달라."*

**회신: 덮어쓴다. coalesce 하지 않는다.** 실제 MySQL 스모크(`src/deposit/deposit.smoke.ts`)로
실증했다.

```
PASS  ⭐ 원본이 voucher_no 를 되돌리면 미러도 null 이 된다      null
PASS  ⭐ 원본이 거래처를 떼면 미러도 null 이 된다               {"name":null,"code":null}
PASS  되돌림 동기화에도 운영자 매칭은 여전히 보존된다            {"type":"SETTLEMENT_CODE",...}
```

두 성질이 **동시에** 성립하는 것이 핵심이다.

| 컬럼 부류 | 동기화 동작 | 이유 |
|---|---|---|
| 원본 미러 컬럼 | **null 로도 덮어쓴다** | coalesce 하면 프리미엄만 옛 거래처를 붙들고 있어 거울이 깨진다 |
| 프리미엄 소유 컬럼<br>(`matched_owner_type` / `matched_owner_id` / `match_status`) | **건드리지 않는다** | 운영자가 방금 지정한 매칭이 다음 주기에 조용히 UNMATCHED 로 되돌아가면 안 된다 |

구현은 `deposit.sync.service.ts` 의 `orUpdate()` 에 **갱신 컬럼을 명시적으로 열거**하는 방식이다.
엔티티 전체를 `save()` 하거나 목록을 생략하면 두 번째 성질이 깨진다.

## 3. 멱등성 — `dedupKey` 가 계약의 핵심

프리미엄은 받은 행을 `dedupKey` 기준으로 upsert 한다. 그래서:

- **같은 건이 여러 번 와도 안전하다.** 프리미엄은 매 주기 최근 구간을 통째로 다시 요청한다.
  중복 수신은 오류가 아니라 빠짐을 메우는 안전장치다.
- **`dedupKey` 는 절대 바뀌면 안 된다.** 같은 거래가 어제와 오늘 다른 지문으로 오면
  프리미엄에 **같은 입금이 두 줄** 생긴다. 회계 반영으로 `voucherNo` 가 나중에 채워져도
  지문이 안 바뀌도록 되어 있는 현재 설계(지문 = 계좌\|일자\|구분\|금액\|잔액\|입금처)를 유지할 것.
- 지문 산식 변경은 **반드시 사전 협의**. 프리미엄 쪽 재매핑이 필요하다.

## 4. 프리미엄의 호출 패턴 (부하 예측)

| 항목 | 값 | 설정 키 |
|---|---|---|
| 주기 | 5분 | (cron 고정) |
| 범위 | 최근 **30일** 을 통째로 재요청 | `DEPOSIT_SYNC_RESYNC_DAYS` |
| 페이지 크기 | 500 | `DEPOSIT_SYNC_PAGE_SIZE` |
| 정상 시 요청 수 | 30일 ≈ 500건 → 1~2회 | |
| 최초 백필 | 전체 1회 (약 4,900건 → 10회 내외) | `DEPOSIT_SYNC_BACKFILL_FROM` |

**왜 증분(`updatedSince`)이 아니라 통째로 다시 받나:** 증분은 경계 시각·시계 오차에서 한 건씩
샌다. 멱등 upsert 가 있으니 통째로 다시 받는 쪽이 단순하고 안전하며, 이 규모(하루 수십 건)에서
비용은 무시할 만하다. 규모가 커지면 그때 증분 파라미터를 논의한다.

> ### size 상한 — 초과 시 **400** (2026-08-05 상호 확정)
>
> | | |
> |---|---|
> | 상대 상한 | **2000**. 초과 요청은 **400 으로 거부**한다 — 조용히 깎지 않는다 |
> | 프리미엄 사용값 | **500** (통과) |
> | 프리미엄 자체 clamp | 1000 |
>
> **원래 프리미엄이 요청한 것이 이 400 이다.** 순회 종료 조건이 `받은 개수 < 요청 개수` 라서,
> 상대가 요청 `size` 를 말없이 깎으면 첫 페이지부터 종료 조건이 참이 되어 **에러 없이 한 페이지만
> 읽고 끝난다.** 상대가 이 지적을 수용해 클램핑을 없애고 400 을 반환하도록 구현했다(테스트 포함).
>
> 그래서 무음 유실 경로는 닫혔다. 프리미엄의 자체 clamp(1000)는 이제 **다른 이유로** 남아 있다 —
> `DEPOSIT_SYNC_PAGE_SIZE` 를 잘못 크게 설정하면 매 주기 400(영구 실패)으로 동기화가 통째로
> 멈추는데, clamp 가 그 설정 실수를 흡수한다.
>
> 상대가 상한을 **500 아래로 낮출 계획이 생기면 사전 통지**하기로 했다.

## 5. 보안

| 항목 | 요구 |
|---|---|
| 전송 | **HTTPS 필수.** 예금주 실명 + 금액이 평문으로 오간다 |
| 인증 | `X-API-KEY` 헤더. 불일치 시 **401** (fail-closed 확인함) |
| 출처 제한 | erp_macro 쪽에서 **프리미엄 서버 IP 만** 인바운드 허용 |
| 노출 범위 | `/api/*` 외에는 인터넷에 열지 말 것. 특히 `/admin/*` (런북 §6) |

> 스크래핑 서버에는 ECOUNT 로그인이 통과된 브라우저 프로필이 남아 있다. 그 서버가 뚫리면
> 입금내역뿐 아니라 회계 시스템 접근까지 함께 넘어가므로, 열어 주는 표면을 최소로 잡는다.

**프리미엄 미러의 PII 취급 (2026-08-04 결정):** 상대가 암호화 보관하는 4종
(`depositor` / `depositorRaw` / `erpPartnerName` / `erpPartnerCode`)을 **미러도 암호화 저장**한다.
사본이 원본보다 보호 수준이 낮으면 미러를 두는 것 자체가 보안 등급을 낮추는 일이 되기 때문이다.

- 스킴은 이 레포의 기존 PII 저장 방식을 재사용한다 — `CryptoCipher.encryptDeliveryTarget`
  (AES-256-CBC, 고정 IV). `delivery_send_history.target` 과 동일하며 transformer 없이
  서비스 계층에서 명시 암/복호한다(레포 관례).
- **부분검색은 유지된다.** 고정 IV 라 같은 평문이 늘 같은 암호문이 되므로, 고유 암호문을
  뽑아 복호화한 뒤 평문으로 부분일치를 판정하고 살아남은 암호문으로 되짚는다
  (실측: 4,893건 → 고유 입금처 1,133개).
- `accountNo` 는 ECOUNT 가 이미 마스킹한 값(`280***01757104`)이라 암호화 대상에서 제외한다.
- 입금처 검색은 `activity_log` 에 `PII_SEARCH` 로 남기며, 검색어는 마스킹해 기록한다
  (감사 로그가 또 하나의 평문 PII 저장소가 되지 않도록).

## 6. 에러 규약

| 상황 | 상태 코드 | 프리미엄의 대응 |
|---|---|---|
| 키 불일치/누락 | 401 | **즉시 중단 + 에러 로그.** 재시도해도 소용없음 |
| 파라미터 오류 | 400 / 404 | 즉시 중단 + 에러 로그 (계약 불일치 의심) |
| 서버 오류·타임아웃 | 5xx / timeout | 이번 주기 포기, **다음 주기에 재시도** (멱등이라 안전) |
| 응답 형태 불일치 | 200 이지만 `content` 없음 | 일시 실패로 처리 (프록시 오류 페이지 등) |

프리미엄은 실패를 조용히 삼키지 않는다. 부분 실패해도 다음 주기가 같은 구간을 다시 요청하므로
데이터는 자연히 수렴한다.

## 7. 프리미엄 쪽 설정

```
ERP_MACRO_API_BASE_URL=https://<스크래핑 서버 주소>
ERP_MACRO_API_KEY=<발급 키>
ERP_MACRO_API_TIMEOUT_MS=30000
DEPOSIT_SYNC_ENABLED=false        # 상대 API·회선 준비 후 true
DEPOSIT_SYNC_RESYNC_DAYS=30
DEPOSIT_SYNC_PAGE_SIZE=500
DEPOSIT_SYNC_BACKFILL_FROM=2020-01-01
```

**켜는 순서**
1. `migration/bank-deposit-mirror.sql` 적용 (프리미엄 DB)
2. 프리미엄 코드 배포 (동기화는 꺼진 상태)
3. erp_macro 기동 + `POLLING_ENABLED=true` 로 데이터 적재 확인
4. `curl -H "X-API-KEY: <키>" https://<host>/api/deposits` 로 프리미엄 서버에서 도달 확인
5. 프리미엄 env 3줄 주입 + `DEPOSIT_SYNC_ENABLED=true` 재기동 → 5분 뒤 미러 확인
