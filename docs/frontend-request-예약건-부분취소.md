# [프론트 요청] 예약 발송건만 부분취소 + 예치금/여신 복구 (197-16)

작성일: 2026-07-22 / 갱신: 2026-07-23 (백엔드 구현·리뷰 완료 반영)
대상 레포: epopkon-premium-front
관련 화면: 발송관리 상세(`SendGeneralDetailPage`, `SendSSGDetailPage`)

## 배경 (왜)

상품마다 예약시간을 다르게 걸면, 한 주문 안에서 **일부는 이미 발송되고 일부는 아직 대기**인 상태가 생깁니다.
이때 지금은 취소 버튼이 아예 안 먹습니다.

원인은 백엔드의 취소 판정이 **주문 단위**라서입니다. 예약 상품행들의 발송예정시각 중 **가장 이른 값 하나**로
주문 전체를 판정하는데, 이미 지나간 시각이 섞여 있으면 "발송 10분 전이 지났다"로 막힙니다.
남은 대기 건은 아직 하루가 남았어도 같이 막힙니다.

이걸 **발송건 단위**로 내립니다. 대기 중인 발송건만 골라 취소하고, 그만큼만 예치금/여신을 되돌립니다.

> 취소된 건을 고쳐서 다시 보내는 기능(티켓 5번)은 **후속 범위**입니다. 이번엔 취소까지입니다.

## 백엔드 변경 사항 (구현·배포 준비 완료)

### 1) `POST /order/delivery-cancel` — `deliveryIds` 필드 추가 (선택값)

```jsonc
{
  "id": 1001,                        // 주문 id (기존)
  "cancelReason": "고객 요청",        // 취소 사유 (기존, 최대 1000자)
  "deliveryIds": [9003, 9004, 9005]  // ★ 신규(선택): 취소할 발송건 id 목록
}
```

**`deliveryIds` 는 선택값입니다. 하위호환이 유지됩니다.**

| `deliveryIds` | 동작 |
|---|---|
| **미전송(필드 생략)** | 종전과 100% 동일 — 주문 전체 취소 |
| **전송** | 지정한 발송건만 취소 + 그 몫만 환불 |

- 기존 프론트는 **손대지 않아도 계속 동작**합니다(전체취소). 준비되면 `deliveryIds` 를 붙이면 됩니다.
- **빈 배열 `[]` 은 400** 입니다. 전체취소를 의도하면 필드를 **생략**하세요(빈 배열 금지).
- 강제 400 구간이 없으므로 **프론트/백엔드 동시 배포 조율이 필요 없습니다.**

> ⚠️ **`deliveryIds` 는 `GET /order/detail/:id` 응답의 실제 `order_delivery.id` 여야 합니다.**
> 화면에서 클라이언트가 생성한 임시 행 id(아래 "프론트 현황 3" 참고)를 보내면 안 됩니다.

### 2) 취소 가능한 발송건 판정 기준 (백엔드가 서버에서 재검증)

백엔드가 아래를 **모두** 만족하는 발송건만 취소합니다. 프론트 버튼 활성 조건 참고용이며,
**최종 판정은 서버가 합니다**(프론트 조건은 UX용, 서버가 SoT).

- 발송 대기 상태 (`status === 'WAIT'`)
- 아직 실제로 나가지 않음 (`actualSendAt` 없음)
- 발송 배치가 아직 집어가지 않음 (`claimedAt` 없음)
- 쿠폰/PIN 이 아직 발급되지 않음 (`couponIssuedAt` 없음 **그리고** `barCode` 없음)
- **발송예정시각까지 10분 이상 남음**
- 외부 API 주문이 아님

추가로 **주문 레벨 조건**:
- 주문이 **발송확정(`DELIVERY_CONFIRMED`) 상태**여야 함 (그 전엔 취소할 발송건이 없음)
- **SSG 주문은 아직 미지원**(아래 3-b) — 400 으로 거부 + 안내
- 지갑(정산 정보) 없는 구주문은 미지원 — 400 으로 거부 + 안내

`GET /order/detail/:id` 응답의 `productList[].orderDeliveryList[]` 에 발송건별 `id`, `status`,
발송예정시각이 내려가므로 별도 API 없이 목록을 만들 수 있습니다.

### 3-a) 응답 코드 — 형식/판정 (400)

| 상황 | 백엔드 메시지(요지) | 프론트 처리 |
|---|---|---|
| `deliveryIds` 형식 오류(빈 배열/중복/소수·음수/**1000개 초과**) | 형식 오류 | 미리 막기(아래 D) |
| 요청 id 중 취소 불가가 하나라도 있음(**전량 거부**) | "취소할 수 없는 발송건이 포함돼 있습니다: {id들}. 이미 발송됐거나 발송 준비가 시작됐거나, 발송이 임박(10분 이내)했거나, 이 주문의 발송건이 아니거나, 외부 API 주문일 수 있습니다." | 메시지 표시 + 상세 재조회 |
| 발송확정 상태 아님 | "발송 대기 상태의 주문만 발송건별로 취소할 수 있습니다." | 메시지 표시 |
| SSG 주문 | "SSG 주문은 아직 발송건별 취소를 지원하지 않습니다. 주문 전체 취소를 이용해 주세요." | 3-b 참고 |
| 지갑 정보 없는 구주문 | "이 주문은 발송건별 취소를 지원하지 않습니다(정산 정보 없음). 주문 전체 취소를 이용해 주세요." | 메시지 표시 |

> **전량 거부**: 요청 3건 중 1건이라도 취소 불가면 **아무것도 취소되지 않습니다**(부분 성공 없음).
> 이렇게 설계한 이유 — 부분 성공을 허용하면 "N건 취소한 줄 알았는데 M건만" 상황에서 이미 커밋된 뒤라
> 되돌릴 수 없기 때문입니다.

### 3-b) 응답 코드 — 경합/멱등 (409, "아무것도 안 됐다")

| 상황 | 백엔드 메시지 | 프론트 처리 |
|---|---|---|
| 취소 중 그 발송건이 발송 단계로 넘어감(경합) | "취소 처리 중 일부 발송건이 발송 단계로 넘어가 취소하지 못했습니다. 아무것도 취소되지 않았고 환불도 일어나지 않았습니다. 발송 결과를 확인한 뒤 남은 대기 건만 다시 취소해 주세요." | **문구 그대로 노출** + 상세 재조회 |
| 이미 처리된 요청(멱등) | "이미 처리된 취소 요청입니다. 발송 상태를 다시 조회한 뒤 남은 대기 건만 취소해 주세요." | 재조회 유도 |
| 환불 정보(정산 라인) 못 찾음 | "취소 대상 중 환불 정보를 찾지 못한 발송건이 있어 처리하지 못했습니다. 아무것도 취소되지 않았습니다. 고객센터로 문의해 주세요." | 문구 그대로 노출 |

> **409 = "아무것도 취소·환불되지 않았다"** 가 공통 보장입니다. 이 문구를 그대로 보여 주세요 —
> 운영자가 "환불이 반쯤 됐나?" 하고 확인 작업에 들어가는 걸 막아 줍니다.

### 3-c) 성공 응답 (부분취소 전용) — 신규

부분취소가 성공하면 **취소 결과를 본문으로** 돌려줍니다. 돈이 오간 요청이라 화면에서 대사(확인)할 수 있어야 하기 때문입니다.

```jsonc
{
  "canceledIds": [9003, 9004, 9005], // 실제로 취소된 발송건 id (정렬·중복제거됨)
  "refundedAmount": 55000,           // 되돌아간 총액(원) = 예치금 + 여신 + 신용초과
  "remaining": 2                     // 취소 후 남은 발송건 수. 0 이면 주문이 취소 상태로 내려감
}
```

- **전체취소(`deliveryIds` 생략)는 종전대로 본문이 없습니다.** 기존 프론트는 영향 없음.
- 전량 거부 정책상 `canceledIds` 는 항상 요청과 같지만, 중복을 접고 정렬한 값이라 그대로 대조에 쓰면 됩니다.
- **활용**: 완료 토스트에 `"{canceledIds.length}건 취소 · {refundedAmount.toLocaleString()}원 환불"` 로 표시하면
  아래 B(무엇이 취소되는지 명시)의 사후 확인까지 한 번에 됩니다. `remaining === 0` 이면 주문 자체가
  취소됐으므로 목록으로 보내도 됩니다(그 외에는 아래 E대로 상세 재조회).

### 4) 고객 통지 (자동)

DIRECT 고객사 주문(대행 아님 + 외부 회사 + 작성자 CORPORATE_ADMIN)은 부분취소 시
**주문자 대표 이메일로 "예약 발송 건이 일부 취소되었습니다" 메일이 자동 발송**됩니다
(취소/남은 건수·사유·시각 포함). 대기 건을 **전량** 취소하면 사실상 전체취소이므로
"주문이 취소되었습니다" 문안으로 나갑니다. **프론트가 별도로 할 일은 없습니다** — 참고용.

## 프론트 변경 요청

### A. 발송건 선택 UI (발송관리 상세)

지금은 주문당 "주문취소" 버튼 하나입니다. 여기에 **취소할 발송건을 고르는 단계**가 필요합니다.

```
┌──────────────────────────────────────────────────┐
│  발송 취소                                        │
├──────────────────────────────────────────────────┤
│  취소할 발송 건을 선택해 주세요.                    │
│                                                   │
│  ▼ 상품A (즉시발송)                                │
│     ☒ 010-****-1234   발송완료 07-21 10:02  [취소 불가] │
│     ☒ 010-****-5678   발송완료 07-21 10:02  [취소 불가] │
│                                                   │
│  ▼ 상품B (예약발송 07-22 18:00)                    │
│     ☑ 010-****-1111   발송대기                     │
│     ☑ 010-****-2222   발송대기                     │
│     ☑ 010-****-3333   발송대기                     │
│                                                   │
│  선택: 3건 / 취소 가능: 3건                        │
│                                                   │
│  취소 사유 *                                       │
│  ┌──────────────────────────────────────────────┐│
│  │                                              ││
│  └──────────────────────────────────────────────┘│
│                                    0 / 1000자     │
│                                                   │
│         [선택 건 취소]        [닫기]               │
└──────────────────────────────────────────────────┘
```

요구사항:
- 취소 **불가** 사유(발송완료/발송임박)를 건별로 보여줄 것. 체크박스는 비활성.
- 기본 선택은 **취소 가능한 건 전체**.
- 하단에 "선택 N건" 을 항상 표시 — 사용자가 무엇이 취소되는지 알고 누르게 할 것.
- **보내는 `deliveryIds` 는 상세 API 의 실제 `order_delivery.id`.** (프론트 현황 3 참고)

### B. "무엇이 취소되는지" 명시 (중요)

가장 조심할 부분입니다. 지금 버튼 문구가 "주문취소"라, 사용자는 **주문 전체가 취소된다고 생각**합니다.
실제로는 일부만 취소되는데요.

확인 단계에서 이렇게 표시해 주세요:

```
5건 중 3건이 취소됩니다.
이미 발송된 2건은 취소되지 않으며, 환불도 3건분만 이루어집니다.
```

이 안내가 없으면 "전체 취소한 줄 알았는데 왜 일부만?" 클레임이 납니다.

### C. 취소 사유 입력 (기존 모달 재사용)

기존 취소사유 모달을 그대로 쓰되, 선택 UI와 합쳐 주세요. 최대 1000자 제한은 동일합니다.

### D. `deliveryIds` 형식 규칙 (미리 막아 400 방지)

- 빈 배열 불가 → 전체취소는 **필드 생략**(빈 배열로 보내지 말 것)
- **중복 불가** — 체크박스 상태를 합칠 때 `Set` 으로 정리
- 정수, 1 이상
- **최대 1,000건** (예전 안내의 10,000 아님)

### E. 취소 후 처리

- **성공(부분취소)**: 목록으로 `router.replace` 하지 말고 **상세를 재조회**해 남은 발송건 상태를 갱신
  (일부만 취소됐으므로 주문은 아직 살아 있음). 프론트 현황 4 참고.
- **409**: 반드시 상세 재조회(그 사이 발송 상태가 바뀜) + 위 안내 문구 노출.

## 프론트 현황 (조사 시점: 2026-07-22, epopkon-premium-front — 착수 전 현행 코드 확인 필요)

부분취소 붙이기 전에 걸릴 수 있는 **현행 코드 함정**입니다. 착수 시 최신 코드로 재확인 부탁드립니다.

1. **호출부 2곳**: `SendGeneralDetailPage.tsx`, `SendSSGDetailPage.tsx`. 현재 `{ id, cancelReason }` 만 전송.
2. **에러 뭉개짐**: 취소 실패가 전부 `alert('주문 취소에 실패했습니다.')` 로 수렴 →
   위 400/409 백엔드 메시지가 사용자에게 안 보임. **서버 메시지를 그대로 노출**하도록 고쳐야 함.
3. **임시 행 id 함정**: `ProductDeliveryTable` 이 표시용으로 `Date.now()` 기반 **가짜 행 50개**를 덧붙이는
   코드가 있었음. 이 가짜 id 를 `deliveryIds` 로 보내면 안 됨 — 상세 API 의 실제 `order_delivery.id` 사용.
4. **성공 후 이동**: 취소 성공 시 `router.replace(목록)` 으로 빠지는데, 부분취소는 주문이 남아 있으므로
   목록 이동이 아니라 상세 재조회가 맞음(E 참고).
5. **CANCEL 배지 색**: 취소 상태 배지가 초록(`bg-success`)으로 렌더됨 — 취소가 성공처럼 보임. 색 조정 필요.
